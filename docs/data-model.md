## kopn 승인용 한 장 요약 (v4.2)

이 앱이 **무엇을 저장하고, 누가 볼 수 있고, 언제 지우는지**만 모았다. 아래 "운영진"은 팀장과 운영진을 함께 가리킨다.
"못 본다"는 앱 화면에서 숨기는 것뿐 아니라, 앱을 조작해도 서버가 거절한다는 뜻이다.

**계정·프로필**
- 로그인 방법은 안드로이드 카카오·구글, 아이폰 카카오·구글·애플이다.
- 로그인 서비스가 인증한 이메일이 같으면 어느 방법으로 들어와도 **같은 계정**이다(Supabase 기본 자동 합치기). 이메일이 다르거나 인증되지 않았으면 별개 계정이다. 사용자가 직접 계정을 연결하거나 합치는 기능은 없다.
- 그래서 계정 하나에 로그인 방법이 여러 개 붙을 수 있다. 새 방법이 기존 계정에 붙어도 동의를 다시 받지 않는다(이미 동의 기록이 있음). 애플 "이메일 가리기"를 쓰면 이메일이 달라 별개 계정이 된다.
- 아이폰에서 애플로 가입한 사람이 안드로이드로 오면(안드로이드에는 애플 로그인 없음), 애플 계정의 실제 이메일이 카카오·구글의 인증된 이메일과 같을 때만 기존 계정으로 들어가고, 아니면 새로 가입한다.
- 프로필은 사람당 하나: 팀에서 쓸 이름(8자)과 한줄 자기소개(20자). 본인과 지금 같은 팀 사람이 본다. 이름의 보이지 않는 문자는 저장 때 지운다.
- 가입 때 "만 14세 이상", 약관·개인정보 동의(필수), 부상 정보 동의(선택)의 버전과 시각을 저장한다. 본인만 본다. 회원 탈퇴하면 함께 지운다.
- 선호 포지션(골키퍼 포함 최대 3개)과 전문 골키퍼 여부는 본인과 소속 팀 운영진만 본다.
- 회원 탈퇴하면 그 사람의 기록을 전부 지운다(최근 경기 기록, 출석·수상 횟수, 부상, 동의 기록 포함). 계정에 붙은 로그인 방법도 모두 지우고 카카오·구글·애플 연결을 각각 해제한다. 팀장은 먼저 위임하거나 해체해야 한다.

**팀**
- 팀 이름(10자), 6자리 팀 식별코드(바꿀 수 없음, 팀원 모두 봄), 로고, 정기 운동일, 지정 풋살장(카카오맵), 인원 모집 여부를 저장한다. 팀원은 모두 본다.
- 팀 밖 사람은 팀 찾기 결과로 이름·식별코드·로고·운동일·구장 이름·인원 수·모집 여부만 본다. 모집 중일 때만 가입 신청할 수 있다(신청 뒤 모집을 꺼도 낸 신청은 유효).
- 실력 등급은 팀마다 따로 저장하고 **운영진만** 본다. 일반 팀원은 자기 등급도 못 보고, 팀 배치·공유 이미지에도 나오지 않는다.
- 그룹·라이벌 설정은 운영진만 본다. 초대 코드(24시간, 팀당 1개)와 가입 신청은 신청자 본인과 운영진이 본다.
- 팀을 떠나면 실력 등급·그룹·라이벌은 지우고, 남은 최근 경기 기록에는 **이름·프로필이 빈칸**으로 보인다. 본인의 출석·수상 횟수는 본인에게 남는다.

**일정·참석**
- 일정(날짜·시간·장소·정원·마감 시각)과 각자의 참석·불참·대기 응답을 저장한다. 그 팀 팀원 모두가 명단을 본다.
- 게스트는 이름(팀원 모두)과 포지션(운영진만)을 저장한다. 매번 새로 입력한다.
- 시간은 한국 시간 고정. 팀 설정을 바꿔도 이미 만든 일정은 그대로다.

**팀 나누기**
- 배치 결과(팀 블록, 조끼 색, 누가 어느 팀인지)를 저장한다. 운영진은 언제나, 팀원은 확정된 뒤에만 본다. 실력 등급 합계나 팀 점수는 저장하지 않는다.
- 확정 뒤 고치면 변경 이력이 남는다(운영진만 봄). 경기 시작 전 수정은 참석자에게 알림이 가고, 경기 시작 후 수정은 알림이 가지 않는다.
- 못 온 사람은 경기 종료 전까지 배치에서 빼면 출석·투표 대상에서 빠진다. 경기가 끝나 투표가 열리면 명단이 고정된다.

**투표**
- POM·오늘의 골은 "누가 투표했는지"와 "누가 몇 표 받았는지"를 따로 저장하고, **누가 누구를 찍었는지는 아예 저장하지 않는다.** 팀장도 알 수 없다.
- 득표수는 최근 10경기 범위에서 모두 저장하지만 앱에서는 누구도 볼 수 없고, 화면에는 1위만(동점이면 공동 1위) 나온다.
- 내가 투표했는지는 나만 본다. 한 번 낸 표는 바꿀 수 없다.

**기록 보관 (v4 핵심)**
- 팀마다 **최근 10경기**의 상세 기록(일정, 참석 응답, 게스트, 배치, 변경 이력, 투표 참여, 득표수, 1위)만 남기고, 그보다 오래된 경기는 서버가 자동으로 지운다.
- 대신 **사람·팀·시즌별 숫자**를 영구로 남긴다: 출석 횟수, POM 1위 횟수, 오늘의 골 1위 횟수. 팀을 떠나도 본인 "내 기록"에 남고, 회원 탈퇴하면 지운다. 출석은 경기 종료 때, 수상은 투표 마감 때 1씩 올린다.
- 2차 팀 리포트용으로 **팀·사람별 월간 출석 수**를 숫자로만 남긴다. 1차에는 아무도 보지 않는다.
- "10경기"는 끝났고 취소되지 않은 일정으로 센다(배치를 안 짠 경기 포함). 경기가 끝나면 배치를 고칠 수 없다. 팀이 해체되면 남은 상세 기록도 지운다.
- 2차 출석률 계산용으로 **팀별 월간 경기 수**를 숫자로 남긴다.
- **참석 투표 참여율**: 팀·사람·월별로 참석 투표 대상 횟수와 응답 횟수를 남기고(부상 중이면 응답으로 봄), 본인 "내 기록"에 퍼센트로 보여준다. 다른 사람은 못 본다.

**부상**
- 부상 정보 동의(선택)를 한 사람만 부상을 등록한다. 가입 때 안 했어도 나중에 동의할 수 있다.
- 부상 기록(예상 복귀일, 20자 메모)과 변경 이력(등록·연장·회복)을 동의 철회나 회원 탈퇴 전까지 보관한다(팀을 떠나도 유지).
- 진행 중인 부상은 본인과 같은 팀 팀원 모두가 메모까지 본다. 지난 기록과 이력은 1차에는 본인만 보고, 2차 운영진 팀 리포트에 쓴다(동의 문구에 적음).
- 동의를 철회하면 즉시 팀원에게 안 보이고 부상 기록과 이력을 모두 지운다.

**알림**
- 푸시와 앱 안 알림함 둘 다로 보낸다. 알림함에는 바로 쌓이고, 푸시만 밤 0시~8시를 피해 8시에 보낸다.
- 알림함은 본인만 보고 30일 보관한다. 떠난 팀 알림이나 지워진 경기 알림은 남지만 눌러도 이동하지 않는다.
- 문구에 사람 이름이 들어간다. 그 사람이 회원 탈퇴하면 그 알림을 지운다. 실력 등급·득표수·부상 메모·초대 코드는 넣지 않는다.

**2차 대비**
- 구독 이용 권한을 적을 칸을 1차부터 만들어 두고 비워 둔다. 결제 정보(카드·영수증)는 저장하지 않는다.
- 득표수 보기·팀 리포트는 서버가 이용 권한을 다시 확인해서 준다. 1차에는 1위 외에는 아무것도 주지 않는다.
- 2차 득표수 보기는 최근 10경기만 가능하다. 2차 팀 리포트는 월간 출석 수, 최근 10경기 기록, 부상 기록으로 만든다.

**승인 전에 정할 것** (12-2): M-44 안드로이드에서 애플 로그인이 붙은 계정을 탈퇴할 때 애플 연결 해제 방법(12-4 테스트 결과에 따라 질문). 그 밖의 kopn 결정은 모두 반영했다.

## 0. 읽는 법 (kopn용)

- **테이블** = 엑셀 시트 하나라고 생각하면 된다. 한 줄(행)이 한 건의 기록이다.
- **필드** = 시트의 열(칸 제목).
- **누가 읽고/쓸 수 있나** = 데이터베이스가 직접 막는 규칙(RLS). 앱 화면에서 숨기는 것과 별개로, 앱을 조작해도 서버가 거절한다.
- **"서버 함수로만"** = 앱이 표에 직접 쓰지 못하고, 서버에 있는 정해진 절차(예: "참석 투표하기")를 통해서만 바뀐다는 뜻. 규칙 검사(마감 시간, 정원, 본인 투표 금지 등)를 서버가 한 번에 처리한다.
- **탈퇴 시** = 회원 탈퇴(계정 삭제)할 때 그 줄이 어떻게 되는지. "같이 삭제"는 줄이 지워지고, "비움"은 줄은 남고 그 칸만 빈칸이 된다. 2-5에 표 전체를 모았다.

타입 표기:

| 표기 | 뜻 |
| --- | --- |
| ID | 자동으로 붙는 추측 불가능한 고유 번호 (uuid) |
| 글자 | 텍스트 |
| 숫자 | 정수 |
| 날짜·시간 | 시각 (시간대 포함으로 저장) |
| 날짜 | 날짜만 |
| 시각 | 하루 중 시각 (예: 10:00) |
| 예/아니오 | 참·거짓 |
| 선택(…) | 정해진 값 중 하나만 |
| 목록(…) | 여러 값 |

역할 줄임말: **팀장**(owner), **운영진**(manager), **팀원**(member). "팀장·운영진"은 이하 **관리자**로 줄여 쓴다.
"그 팀 팀원" = 그 팀에 현재 소속된 사람 전체(팀장·운영진 포함).
"회원 탈퇴" = 앱 계정 삭제. "팀 탈퇴" = 한 팀에서만 나감. 둘을 구분해 쓴다.

## 2. 계정·프로필

### 2-1. 로그인 계정 (Supabase 제공: `auth.users`, `auth.identities`)

**무엇을 저장하나:** 사람 한 명의 앱 계정(`auth.users`)과, 그 계정에 붙은 **로그인 방법 1개 이상**(`auth.identities`, 방법마다 한 줄). Supabase가 기본으로 제공하는 표를 쓰고 우리가 직접 만들지 않는다. 서버는 Supabase **서울 리전** `[결정됨 Q-024]`.

- **로그인 방법** `[결정됨 Q-030]`: 안드로이드 앱은 카카오·구글, iOS 앱은 카카오·구글·애플. 기기별로 버튼이 다를 뿐 표 구조는 같다. **안드로이드에는 애플 로그인을 넣지 않는다** `[결정됨 Q-050]`.
- **인증된 같은 이메일 = 같은 계정** `[결정됨 Q-063 A]`: 로그인 서비스(카카오·구글·애플)가 **인증했다고 표시한 이메일**이 기존 계정의 이메일과 같으면, 어느 방법으로 들어와도 그 기존 계정으로 로그인된다. Supabase 기본 동작(자동 합치기, automatic identity linking)을 그대로 쓴다. 팀·기록·동의가 모두 이어진다.
  - 배경: Supabase 공식 문서상 자동 합치기를 끄는 설정이 없고, 같은 이메일의 계정 두 개를 만들 수 없다. 그래서 Q-056(같은 이메일도 별개 계정)·Q-059(가입 전 "이전에 ○○로 가입했어요" 안내)·Q-060 1)·2)(안내 화면 세부)를 Q-063이 대체했다.
  - **이메일이 다르거나 인증되지 않았으면 별개 계정**이다(기존 계정과 연동 없음, 팀·기록 이어지지 않음).
  - 카카오가 이메일을 "인증 안 됨"으로 넘기는 경우 Supabase가 별개 계정을 만드는지, 로그인을 거부하는지 `[확인 필요]`(개발 프로젝트에서 테스트, 12-4).
  - 애플 "이메일 가리기"를 쓰면 애플이 대리 이메일을 넘기므로 다른 이메일 → 별개 계정이 된다(막을 방법 없음, 결정과 맞음).
- **사용자가 직접 연결하는 기능 없음** `[결정됨 Q-007-2, Q-008-2, Q-063]`: 로그인 방법을 직접 붙이거나 떼는 화면이 없다. Supabase의 수동 연결(manual linking) 설정은 끈 채로 두고, 앱은 연결·연결 해제 함수를 쓰지 않는다. 계정에 붙은 로그인 방법은 회원 탈퇴 때만 함께 지워진다(2-5).
- **새 로그인 방법이 기존 계정에 붙을 때**: 이미 프로필이 있는 계정이면 바로 로그인된 상태가 되고 가입 단계(2-2)를 다시 거치지 않는다. **동의를 다시 받지 않는다**(동의 기록 8-1은 계정 기준이며 이미 있음) `[결정됨 Q-063]`. 프로필이 아직 없는 계정(가입 도중 그만둔 계정)에 붙으면 평소처럼 가입 단계부터 진행한다.
- **폐지(Q-063)**: 가입 직전 같은 이메일 안내와 [새로 가입]/[기존 방법으로 로그인] 선택, 같은 이메일 확인 서버 함수(13장 S-12), [기존 방법으로 로그인]을 고르면 "방금 생긴 빈 로그인 계정을 서버가 바로 지우는" 처리, 프로필 만들기 함수의 "로그인 방법이 1개인지" 확인은 모두 없앤다.
- **가입 도중 그만둔 계정 정리**(유지): 프로필 없이 24시간 지난 로그인 계정은 예약 작업이 지운다(저장된 개인 데이터가 없으므로 사용자에게 보이는 변화 없음).
- **아이폰에서 애플로 가입한 사람이 안드로이드로 바꾸면** `[결정됨 Q-050, Q-063]`: 안드로이드에는 애플 버튼이 없으므로 카카오나 구글로 로그인한다. 애플 계정의 이메일(이메일 가리기를 쓰지 않은 실제 이메일)이 그 카카오·구글의 인증된 이메일과 같으면 **기존 계정으로 그대로 들어간다**. 이메일이 다르거나 애플 가입 때 이메일 가리기를 썼으면 새로 가입하게 된다(이전 계정과 별개). 표 구조 영향은 없다.

### 2-2. 프로필 `profiles`

**무엇을 저장하나:** 사람당 하나뿐인 프로필. 모든 팀에서 같은 이름과 자기소개가 보인다.
**로그인 직후 누구나 프로필부터 만든다** `[결정됨 Q-010]`. 프로필이 없는 계정은 팀 만들기·가입 신청·팀 찾기 등 모든 서버 함수에서 거절된다.

**가입 단계(프로필 만들기)에서 한 번에 받는 것:** 팀에서 쓸 이름, 자기소개(선택), 선호 포지션·전문 골키퍼, **만 14세 이상 확인**(필수) `[결정됨 Q-023]`, **이용약관·개인정보 수집·이용 동의**(필수) `[결정됨 Q-053]`, **부상 정보 수집·이용 동의**(선택) `[결정됨 Q-049]`. 서버 함수 하나가 프로필·선호 포지션·동의 기록(8-1)을 함께 만든다. 부상 동의를 하지 않아도 가입된다(부상 등록만 불가, 나중에 동의 가능). 문구는 docs/consent-texts.md `[결정됨 Q-057]`.

| 이름 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| user_id | ID | 필수 | 로그인 계정 번호. 계정당 프로필 1개. **탈퇴 시 같이 삭제** |
| display_name | 글자 | 필수 | 팀에서 쓸 이름(실명 또는 별명). **1~8자, 중복 허용** `[결정됨 Q-011]`. 한 줄, 이모지·특수문자 허용, 가운데 연속 공백은 하나로 `[결정됨 Q-034]`. **보이지 않는 문자는 저장 때 자동 삭제** `[결정됨 Q-048]`(11장 14번) |

- 글자 수는 **눈에 보이는 글자 단위**(이모지 1개 = 1자), 앞뒤 공백 제거 후 셈, 줄바꿈 불가 `[결정됨 Q-012]`. 데이터베이스 검사 방식은 11장 14번.
- 만들기: 서버 함수로만(위 "가입 단계" 참고).
- 읽기: 본인 / 나와 같은 팀에 현재 소속된 사람 / 내 팀에 **대기 중인** 가입 신청을 낸 사람(관리자만, 신청 처리용, S-18).
- **떠난 팀원은 남은 기록에서 공란** `[결정됨 Q-058 5번]` (v3의 Q-040 "이름 그대로", Q-055 "지금 프로필 이름"을 대체): 팀을 떠난 사람(팀 탈퇴·내보내기)은 그 팀에 남은 최근 10경기 기록(배치 명단·투표 대상자·1위)에서 **이름·프로필이 빈칸**으로 보인다. 기록 줄은 지우지 않는다(본인 카운트와 재가입 시 이어짐 때문, 7-3).

  - v3의 "떠난 팀원 이름만 주는 서버 함수"는 **삭제**한다(필요 없어짐).
  - 다시 가입하면 현재 팀원이 되므로 남아 있는 최근 기록에 이름이 다시 보인다.
  - 회원 탈퇴한 사람은 줄 자체가 지워진다(2-5). 즉 떠난 사람 = 빈칸 한 자리, 회원 탈퇴한 사람 = 자리 없음.
- 고치기: 본인만. `age_14_confirmed_at`, `user_id`, `created_at`은 고칠 수 없음(칸 단위 권한).

### 2-3. 선호 포지션·전문 골키퍼 `profile_play_prefs`

**무엇을 저장하나:** 팀 나누기에 쓰는 본인 정보(선호 포지션, 전문 골키퍼 여부). 팀원 명단에 보이지 않게 하려고 프로필과 표를 나눴다.

| 이름 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| user_id | ID | 필수 | 프로필 주인. **탈퇴 시 같이 삭제** |
| positions | 목록(골키퍼·수비·중앙·측면·공격) | 필수 | **골키퍼 포함 1~3개**, 중복 없음, 순서 없음 `[결정됨 Q-035]` |
| is_dedicated_gk | 예/아니오 | 필수 | 전문 골키퍼. 기본 아니오 |
| updated_at | 날짜·시간 | 필수 | 마지막 수정 시각 |

- 저장 규칙(데이터베이스 검사, 앱을 조작해도 거절):
  - positions는 1~3개, 중복 없음(골키퍼도 3개 안에 포함) `[결정됨 Q-035]`.
  - **전문 골키퍼이면 positions에 골키퍼가 반드시 들어 있어야 한다** `[결정됨 Q-019]`.
  - 두 규칙을 합치면 "전문 골키퍼 + 골키퍼 아닌 3개"는 저장될 수 없다. 앱은 이 상태에서 전문 골키퍼 체크를 막고 "포지션을 하나 빼주세요"로 안내한다 `[결정됨 Q-035]`. 골키퍼가 없고 2개 이하이면 체크할 때 골키퍼를 자동 선택한다 `[결정됨 Q-019]`.
- 쓰기: 본인만 (관리자도 수정 불가).
- 읽기: 본인 + 내가 소속된 팀의 관리자(팀 나누기용) + 대기 중 가입 신청을 받은 팀의 관리자. 일반 팀원은 읽기 불가 `[결정됨 Q-017]`.

### 2-5. 회원 탈퇴 (계정 삭제) `[결정됨 Q-009]`

**결정:** 앱 안에서 회원 탈퇴 가능. 탈퇴하면 **그 사람의 데이터를 전부 삭제**한다(남아 있는 최근 경기 기록, 시즌별 출석·수상 카운트, 월간 출석 수, 부상, 동의 기록 포함). "탈퇴한 회원"으로 익명 보존하지 않는다.

**절차 (서버 함수 하나가 한 번에 처리, 서비스 키는 서버에만):**
1. 본인 확인(로그인된 본인만, 다른 사람 ID를 받지 않음).
2. **현재 팀장인 팀(해체 안 된 팀)이 하나라도 있으면 거절** — 위임 또는 해체 후에만 탈퇴 가능 `[결정됨 Q-037]`.
3. 다가오는 일정에 "참석"이었으면 불참으로 바꾼 것과 똑같이 **대기 1번을 참석으로 자동 전환하고 알림** `[결정됨 Q-038]`. 열려 있는 투표 처리(아래).
4. 그 계정에 **붙은 로그인 방법 모두**(v4.2: 한 계정에 여러 개일 수 있음, Q-063)에 대해 각각 외부 서비스 정리: 카카오 "연결 끊기", 구글 토큰 철회, **애플 토큰 철회**(애플 로그인이 붙은 경우, 애플 심사 요구) `[결정됨 Q-030]`. 서버는 외부 로그인 토큰을 저장하지 않는 것을 원칙으로 한다. 철회에 필요한 값을 얻는 방법은 `[확인 필요]`(12-4). 안드로이드에서 애플이 붙은 계정을 탈퇴할 때(안드로이드에는 애플 로그인이 없어 "탈퇴 직전 다시 로그인" 방식을 쓸 수 없음) 애플 철회를 어떻게 할지 `[미결 M-44]`.
5. 로고 등 저장소 파일 중 본인 소유가 있으면 삭제(1차에는 개인 사진이 없어 해당 없음).
6. 로그인 계정(`auth.users`) 삭제 → 그 계정에 붙은 로그인 방법(`auth.identities`) 줄도 모두 함께 지워지고, 아래 표의 삭제 동작이 연쇄로 적용된다.

v4.2(Q-063): 인증된 같은 이메일로 들어온 로그인 방법은 모두 한 계정에 붙어 있으므로 한 번의 탈퇴로 함께 지워진다. 이메일이 달라(또는 인증되지 않아) 따로 생긴 계정, 애플 이메일 가리기로 생긴 계정은 별개 계정이므로 함께 지우지 않는다. 각각 따로 탈퇴해야 한다.

**팀 식별코드** `[결정됨 Q-029, Q-051]`
- 용도: (1) **팀 찾기** — 앱에서 코드를 입력하면 그 팀이 바로 나오고, 모집 중일 때만 가입 신청 가능(이름 검색과 같은 규칙). (2) 나중에 대회·이벤트에서 같은 이름 팀을 구분하는 식별 역할(2차 이후, 지금 추가 구조 없음).
- **초대 코드(3-5)와 별개다.** 식별코드로는 모집 꺼진 팀에 신청할 수 없다. 6자리라 사람이 칠 수 있고 추측도 가능하므로, 이 규칙이 무너지면 안 된다.
- 만들기: 팀 생성 때 서버가 32가지 글자(A~Z 중 O·I 제외 24개 + 2~9 8개)로 무작위 6자리를 만든다(약 10억 가지). 겹치면 다시 만든다. 순번·팀 이름에서 만들지 않는다.
- **바꿀 수 없음** `[결정됨 Q-051]`: 앱에서 수정 불가, 재발급 기능 없음(v3 M-31 종결).
- **팀원 전체가 볼 수 있다** `[결정됨 Q-051]`(대회·이벤트 식별용). `teams` 읽기 규칙(그 팀 팀원)으로 이미 충족.
- 입력: **소문자로 쳐도 대문자로 바꿔** 정확히 일치할 때만 찾는다(부분 일치 검색 안 함). 0·O·1·I가 들어간 입력은 그대로 "없는 코드예요" `[결정됨 Q-051]`.
- **틀린 입력 횟수 제한 없음** `[결정됨 Q-051]`. 사람에게 보이는 "잠시 입력 제한"은 두지 않는다. 다만 프로그램으로 코드를 대량 대입해 팀 목록을 긁어가는 것을 막는 **보통 사용에서는 닿지 않는 높은 호출 상한**도 두지 않는다 `[lead 정리 M-37, decisions.md]`.

- 장소 칸 묶음(`venue_*`)은 팀 지정 풋살장과 일정 장소(4-1)가 같은 모양을 쓴다.
- 읽기: 그 팀 팀원. 팀원이 아닌 사람은 표를 직접 읽지 못하고, 아래 서버 함수로 필요한 항목만 받는다.
  - **팀 찾기**(이름 검색 또는 식별코드 입력): **모집 중이 아닌 팀도 포함** `[결정됨 Q-021]`. 이름·식별코드·로고·정기 운동일·구장 이름·팀원 수·모집 여부(화면의 "모집 마감" 표시용)만.
  - 초대 코드 확인: 유효한 코드일 때만, 그 팀의 이름·식별코드·로고만.
  - (security 반영) 두 함수 모두 해체된 팀(`dissolved_at` 있음)을 항상 제외하고, 주소·좌표·장소 번호·만든 사람은 돌려주지 않는다. 이름 검색은 사람당 호출 제한(S-14). **식별코드 입력은 틀린 횟수 제한을 두지 않는다** `[결정됨 Q-051]`(남용 방지 상한은 M-37). 어느 쪽이든 이름 검색으로 이미 보이는 정보 이상은 주지 않는다.
- 쓰기 (칸마다 다름):
  - 관리자가 직접 고칠 수 있는 칸: `name`, `logo_image_path`, `regular_*`, `venue_*`, `is_recruiting` (칸 단위 권한).
  - **`logo_text`: 팀장만.** 칸 단위 권한은 팀장과 운영진을 구분하지 못하므로, 직접 쓰기 칸에서 빼고 팀장 확인을 하는 서버 함수로만 바꾼다 `[결정됨 Q-014]`.
  - **팀 이름을 바꿀 때 로고 자동 갱신** `[결정됨 Q-036, Q-047]`: 서버(트리거)가 **지금 `logo_text`가 바꾸기 전 이름의 기본값(Q-013 규칙)과 같으면** "직접 바꾼 적 없음"으로 보고 새 이름의 기본값으로 다시 만든다. 다르면 그대로 둔다. 팀장이 기본값과 같은 글자로 되돌리면 다시 자동 갱신 대상이 된다(별도 버튼 없음). 운영진이 이름을 바꿔도 같은 규칙. 로고 사진이 있어도 글자 칸은 같은 규칙으로 갱신한다(사진을 지우면 글자 로고가 보이므로).
  - v3의 `logo_text_customized` 칸은 **삭제**했다(Q-047로 "바꾼 적 있음"을 따로 기록할 필요가 없어짐).
  - `team_code`: 앱에서 직접 수정 불가(서버도 바꾸는 함수 없음).
  - `id`, `created_by`, `created_at`, `dissolved_at`, `timezone`: 앱에서 수정 불가. 생성·해체는 서버 함수로만(해체는 팀장, 팀 이름 직접 입력 확인).
  - (security 반영) 그렇지 않으면 운영진이 `dissolved_at`을 직접 써서 팀장 전용인 해체를 우회할 수 있다.
- 로고 사진 저장소 `team-logos` `[결정됨 Q-068 1번]`: **읽기는 로그인한 사람 누구나**(팀원 목록·팀 찾기 결과에 표시), 올리기·지우기는 그 팀 팀장·운영진만. 추측할 수 없는 경로(Q-027 S-10). JPG·PNG, 10MB 이하, 앱에서 정사각형으로 잘라 줄여 저장(Q-067 3번), 사진 위치 정보 제거(S-10 권고). 사진을 바꾸거나 지우거나 팀이 해체되면 파일도 삭제. 세부는 13장 S-10.

### 3-3. 팀 소속 `team_members`

**무엇을 저장하나:** 누가 어느 팀에 어떤 역할로 소속돼 있는지. 팀마다 한 줄씩이라, 한 사람이 여러 팀에 소속될 수 있다.

| --- | --- | --- | --- |

| team_id | ID | 필수 | |
| user_id | ID | 필수 | 탈퇴 시 같이 삭제 |
| role | 선택(owner, manager, member) | 필수 | 팀장·운영진·팀원 |
| status | 선택(active, left, removed, dissolved) | 필수 | 소속 중 / 자진 팀 탈퇴 / 내보내짐 / 팀 해체 |

- 데이터베이스가 보장하는 규칙:
  - 팀당 현재 팀장은 정확히 1명.
  - 팀당 현재 운영진은 최대 2명.
  - 한 사람은 한 팀에 "소속 중" 줄이 최대 1개(재가입하면 새 줄).
- 팀 탈퇴·내보내기·해체 때 줄을 지우지 않고 status만 바꾼다(3-8). 회원 탈퇴 때는 줄을 지운다(2-5).

  - 운영진 지정·해제, 내보내기, 팀장 위임: 팀장만. 위임은 운영진 중에서만, 즉시 적용, 기존 팀장은 운영진으로.

  - 운영진 지정·해제, 팀장 위임 받음, 내보내짐 → 본인에게 알림 `[결정됨 Q-022]` (9장).
  - 팀 탈퇴: 본인. 팀장은 위임 또는 해체 전에는 팀 탈퇴 불가(회원 탈퇴도 같음 `[결정됨 Q-037]`).

### 3-5. 초대 코드 `team_invites`

**무엇을 저장하나:** 관리자가 발급한 초대 코드. 24시간 뒤 자동으로 못 쓰게 된다. **팀 식별코드(3-1)와 별개다** `[결정됨 Q-029]`.
**방식** `[결정됨 Q-002]`: 관리자가 공유한 링크를 열면 웹 페이지가 초대 코드를 보여주고 복사하게 한다. 앱을 설치한 뒤 첫 실행 때(또는 가입 화면에서) 그 코드를 붙여넣는다. 앱이 이미 설치돼 있으면 링크로 바로 열 수 있다. 유료 딥링크 서비스는 쓰지 않는다. 초대 코드 = 초대 링크에 담긴 값(같은 규칙).

| --- | --- | --- | --- |
| id | ID | 필수 | |
| team_id | ID | 필수 | |
| token_hash | 글자 | 필수 | 코드 값의 암호화 지문(SHA-256). **원본은 저장하지 않음** `[결정됨 Q-020]` |
| created_by | ID | 선택 | 발급한 관리자. 탈퇴 시 비움(코드는 유효 유지) |
| created_at | 날짜·시간 | 필수 | 발급 시각. **서버 시계로만 기록, 앱이 지정 불가** |
| expires_at | 날짜·시간 | 필수 | 발급 시각 + 24시간. 트리거가 강제로 채우고 두 칸 수정을 막는다(S-13: 생성 칸으로는 불가) |
| revoked_at | 날짜·시간 | 선택 | 새 코드 발급·팀 해체로 무효화된 시각 |

- 코드 값: 서버가 만든 32바이트 무작위 값(사람이 추측 불가). 붙여넣기 방식이라 길어도 된다(손으로 칠 일 없음). 순번·팀 번호·팀 식별코드 등 추측 가능한 값은 넣지 않는다.
- **팀당 유효한 코드 1개** `[결정됨 Q-020]`: "무효화되지 않은 줄은 팀당 1개"를 데이터베이스 고유 조건으로 보장. 새로 발급하면 서버 함수가 이전 줄에 `revoked_at`을 찍고 새 줄을 만든다(한 번에). 만료만 되고 무효화 안 된 줄도 새 발급 때 같이 무효화한다.
- **24시간 안에 여러 명 사용 가능** `[결정됨 Q-020]`: 사용해도 줄이 닫히지 않는다.
- **다시 복사 불가**: 원본이 없으므로 다시 공유하려면 새로 발급한다(이전 코드 무효).
- **만료는 신청 시각 기준** `[결정됨 Q-020]`: 가입 신청(3-6)을 만든 시각이 만료 전이면 유효. 신청 후 승인이 만료 뒤에 이뤄져도 된다. **신청 후 코드가 재발급(무효화)돼도 이미 낸 신청은 그대로 유효** `[결정됨 Q-042]`.
- 사용 확인: 서버 함수가 "지문 일치 + 현재 시각 < 만료 시각 + 무효화 안 됨 + 팀 해체 안 됨"을 모두 확인. 실패하면 이유 구분 없이 "만료된 초대 코드예요" 처리(어느 코드가 존재했는지 알려주지 않기 위해). 단, 유효했던 코드의 팀이 해체된 경우는 "가입할 수 없는 팀이에요" `[결정됨 Q-067 8번]`(유효한 코드를 가진 사람만 받으므로 코드 존재 여부가 새지 않음). 사람당 가벼운 호출 제한(S-13).
- **링크 페이지** `[보류 Q-039]`: 어디에 둘지는 추후 지정. 페이지는 링크 주소에서 코드를 읽어 보여주기만 하고 데이터베이스에 접근하지 않으므로, 어디에 두든 이 표와 함수는 바뀌지 않는다. 코드 값은 URL의 `#` 뒤에 둔다(웹 서버 접속 기록에 안 남게, S-13).
- 읽기: 그 팀 관리자(발급 이력, 지문 칸은 제외). 팀원·외부인은 직접 읽기 불가.
- 쓰기: 서버 함수로만(발급: 관리자).

### 3-8. 팀 탈퇴·내보내기·해체 때 처리 `[결정됨 Q-015, Q-058]`

v4에서 Q-058로 바뀐 점: "출석·수상 보존"은 **카운트(7-3)와 월간 출석 수(7-4) 보존**을 뜻한다. 경기별 상세 기록은 원래 최근 10경기만 남으므로(7-5), 떠난 사람이 나오는 상세 기록은 시간이 지나면 자연히 지워지고, 남아 있는 동안에는 이름·프로필이 빈칸으로 보인다.

  - **경기 종료 후 배치 수정**: Q-046에 따라 종료 후 수정은 출석·투표에 아무 영향이 없다. 그래서 종료 후에는 **수정을 막는다(서버가 거절)** `[결정됨 Q-061 3번]`.

## 6. POM·오늘의 골 투표

### 핵심: "누가 누구를 찍었는지"를 저장하지 않는 구조

한 표가 들어오면 서버 함수 하나가 한 번에 두 가지만 기록한다.

1. **투표 참여 표시** — "OO가 POM 투표를 했다" (누구를 찍었는지는 없음)
2. **득표 집계** — "△△의 POM 득표 +1" (누가 찍었는지는 없음)

두 기록을 잇는 정보(투표 한 장 단위의 기록)는 어디에도 저장하지 않으므로, 앱 사용자(팀장 포함)는 어떤 경로로도 "누가 누구를 찍었는지" 알아낼 수 없다.
(security 반영) 단, 데이터베이스 최고 권한을 가진 운영자는 투표 진행 중과 백업 보관 기간 동안 데이터베이스 내부 기록(트랜잭션 번호, 변경 로그)으로 일부를 추정할 수 있는 여지가 남는다. 13장 S-02 참고.
그 대신 **한 번 낸 표는 바꾸거나 취소할 수 없다** `[결정됨 Q-027 M-08]`. 제출 전 확인 창을 띄운다.
투표 대상자가 3명 이하인 경기도 1위를 공개한다(소수라 추측될 수 있음은 감수) `[결정됨 Q-027 S-16]`.

### 6-1. 투표 회차 `award_polls`

**무엇을 저장하나:** 경기 하나의 POM·오늘의 골 투표 기간과 상태. 경기당 하나.

### 6-4. 득표 집계 `award_tallies`

**무엇을 저장하나:** 항목별 후보마다 받은 표 수. **최근 10경기 범위에서 전부 저장한다** `[결정됨 Q-058]`. **누가 찍었는지는 없다.**

- **1차 원칙 변경**: CLAUDE.md의 "득표수는 1차부터 모두 저장"은 Q-058에 따라 **"득표수는 최근 10경기 범위에서 모두 저장"**으로 바뀐다. 경기가 최근 10경기에서 밀려나면 그 경기의 득표 집계는 경기와 함께 지워지고, 1위 결과만 수상 카운트(7-3)로 남는다. 시즌 누적 득표수 같은 숫자는 남기지 않는다.
- (참고) 경기와 함께 투표 참여 표시·득표 집계가 지워지므로, 13장 S-02의 운영자 수준 잔여 추정 여지도 그 경기는 백업 보관 기간이 지나면 없어진다.

| 이름 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| match_id | ID | 필수 | |
| category | 선택(pom, goal_of_the_day) | 필수 | |
| candidate_id | ID | 필수 | 후보. 탈퇴 시 같이 삭제 |
| vote_count | 숫자 | 필수 | 받은 표 수 |

- 마지막 변경 시각 같은 칸은 일부러 두지 않는다.
- **읽기: 앱에서 직접 읽기 불가 (팀장 포함 누구도).** 마감 후 서버가 1위를 뽑을 때만 사용.
- 2차에서 "본인 득표수"·"상위 3위"를 보여줄 때도 이 표를 직접 열지 않고, 이용 권한(10장)을 확인하는 서버 함수가 허용된 숫자만 돌려준다.
- 실시간 변경 알림(Realtime) 대상에서 제외한다.
- (security 반영) 투표 회차가 열릴 때 서버가 투표 대상자 전원의 줄을 0표로 미리 만든다. 이 표와 투표 참여 표시 표에는 `updated_at` 자동 갱신 트리거를 달지 않는다.
- (security 반영) 투표 서버 함수는 성공/실패만 돌려주고 갱신된 득표수를 돌려주지 않는다. 앱은 "내가 누구를 찍었는지"를 기기에 저장하거나 분석 도구·오류 보고에 남기지 않는다.

### 6-5. 수상자 `award_winners`

**무엇을 저장하나:** 투표 마감 후 항목별 1위. 동점이면 여러 줄(공동 1위). 표가 하나도 없으면 줄 없음 = "결과 없음". **최근 10경기 범위에서만 남는다**(7-5). 그 이전 경기의 수상은 수상 카운트(7-3)로만 남는다.

- **투표 마감 처리 한 번에**: 이 표에 1위 줄을 만들고, 1위인 사람마다 수상 카운트(7-3)의 해당 항목을 1 올린다(공동 1위는 모두 +1, "결과 없음"이면 올리지 않음). 마감 처리 시점에 팀을 떠난 사람이 1위여도 카운트는 올린다(본인 기록).
- 팀을 떠난 사람의 1위 줄은 남고, 화면에서는 이름 빈칸 `[결정됨 Q-058 5번]`.
- 회원 탈퇴하면 그 사람 줄만 삭제 `[결정됨 Q-009]`. **다시 계산하지 않는다**: 공동 1위 중 남은 사람만 보이거나 "결과 없음" `[결정됨 Q-038]`.
- 읽기: 그 팀 팀원 (마감 후에만 생기므로 진행 중 결과 노출 없음). 쓰기: 서버만.

| 개인 카운트 | 출석 횟수, POM 1위 횟수, 오늘의 골 1위 횟수 | **영구** (팀을 떠나도 유지, 회원 탈퇴 시 삭제) | `member_season_stats` (7-3) |
| 월간 출석 수 | 팀·사람·월별 출석 수 (2차 리포트용) | **영구** (회원 탈퇴 시 삭제) | `monthly_attendance` (7-4) |

**1차 원칙 변경** (CLAUDE.md "출석·부상 기록은 처음부터 저장"): 출석은 첫 경기부터 저장하지만 **경기별 상세는 최근 10경기 범위만** 남고, 그 이전은 개인 카운트와 월간 출석 수(숫자)로만 남는다. 부상 기록은 바뀌지 않는다(8장, 처음부터 저장, 동의 철회·회원 탈퇴 전까지).

### 7-1. 출석 기록 `attendance_records`

**무엇을 저장하나:** 최근 10경기 안에서, 경기마다 실제로 출석한 사람. 경기 기록 화면용이고, 카운트(7-3)·월간 출석 수(7-4)를 올리는 근거다.
**출석 = 경기 종료 시점의 확정 배치 명단(교체 포함, 게스트 제외)** `[결정됨 Q-027 M-10, Q-046]`. 노쇼 표시는 없다 `[결정됨 Q-043]` — 경기 종료 전까지 배치에서 빠진 사람은 기록되지 않는다.

| 이름 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| id | ID | 필수 | |
| match_id | ID | 필수 | 경기 삭제 시 같이 삭제 (최근 10경기에서 밀려나면 함께 지워짐) |
| team_id | ID | 필수 | |
| user_id | ID | 필수 | 팀을 떠나도 줄은 남음(화면에서 이름 빈칸), 회원 탈퇴 시 같이 삭제 |
| season | 숫자 | 필수 | 연도 |
| recorded_at | 날짜·시간 | 필수 | |

- 줄이 있으면 출석.
- 기록 시점: **경기 종료 때 서버 예약 작업**이 확정 배치로 만든다. 배치 미확정·취소 경기는 기록 없음. 경기 종료 뒤 배치를 고쳐도 기록은 바뀌지 않는다 `[결정됨 Q-046]`(종료 후 수정은 서버가 거절, Q-061 3번).
- 같은 처리 안에서 출석한 사람마다 시즌 카운트(7-3)의 출석 수와 월간 출석 수(7-4)를 1씩 올린다. 셋 중 하나만 기록되는 일이 없게 한 번에 처리한다.
- 경기 종료 시점에 그 팀을 이미 떠난(탈퇴한) 사람은 배치에 남아 있어도 기록하지 않는다 `[결정됨 Q-061 6번]`. 조기 퇴근은 시스템이 알 수 없으므로 배치에 있으면 출석이다(팀 탈퇴 때 다가오는 일정 응답이 지워지는 것과 같은 취지. 투표 대상자에서도 빠짐).
- 게스트는 기록하지 않는다.
- 읽기: 1차는 본인 것만(v3과 같음). 2차 팀 구독 리포트는 서버 함수로(10장). 쓰기: 서버만.

### 7-2. 내 기록 (화면, 표가 아님)

v3에서는 출석 기록·수상자 표에서 횟수를 계산했지만, 상세가 10경기만 남으므로 **v4부터 "내 기록"은 시즌별 카운트(7-3)에서 읽는다.** 팀별/전체, 시즌별/누적, 해체된 팀·떠난 팀 포함. 본인 것만 돌려주는 서버 함수 하나로 제공.
v4.2: "내 기록"에는 **참석 투표 참여율**(퍼센트, 7-7에서 계산, 대상 0회면 "기록 없음")도 함께 나온다 `[결정됨 Q-062]`.

### 7-3. 시즌별 출석·수상 카운트 `member_season_stats` (v4 신설)

**무엇을 저장하나:** 한 사람이 한 팀에서 한 시즌 동안 출석한 횟수와 POM·오늘의 골 1위 횟수. **개인별·팀별·시즌별 영구 카운트** `[결정됨 Q-058 2·3번]`.

| 이름 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| user_id | ID | 필수 | 회원 탈퇴 시 같이 삭제 |
| team_id | ID | 필수 | 팀. 팀 줄은 지워지지 않음(해체는 표시만) |
| season | 숫자 | 필수 | 시즌(연도, 경기 시작일 기준 1~12월, 한국 시간). 6-5와 같은 기준 |
| attendance_count | 숫자 | 필수 | 출석 횟수. 기본 0 |
| pom_count | 숫자 | 필수 | POM 1위 횟수(공동 1위 포함). 기본 0 |
| goal_of_the_day_count | 숫자 | 필수 | 오늘의 골 1위 횟수(공동 1위 포함). 기본 0 |
| updated_at | 날짜·시간 | 필수 | |

- (사람, 팀, 시즌) 조합당 한 줄. 처음 출석·수상할 때 서버가 만든다. 숫자는 0 이상.
- **언제 올리나**:

| 사건 | 시점 | 올리는 것 |
| --- | --- | --- |
| 경기 종료 | 경기 종료 시각, 예약 작업(7-1 처리와 같은 처리 안) | 출석한 사람마다 `attendance_count` +1 |
| 투표 마감 | 오픈 + 24시간, 예약 작업(6-5 처리와 같은 처리 안) | 1위인 사람마다 해당 항목 +1 |
| 회원 탈퇴 | 즉시 | 그 사람 줄 전부 삭제 |

- 한 번 올린 숫자는 내리지 않는다. 경기 기록이 지워져도(7-5), 팀을 떠나도, 팀이 해체돼도 그대로다. 예외: 회원 탈퇴(줄 삭제), 회원 탈퇴자가 1위였던 경기에서 다른 사람의 카운트는 바뀌지 않는다(재계산 없음, Q-038).
- 같은 경기를 두 번 세지 않도록, 경기 종료 처리와 투표 마감 처리는 각 경기에 "처리 완료" 표시(`matches.closed_out_at`, `award_polls.status`)를 같은 처리 안에서 남기고, 이미 처리된 경기는 건너뛴다.
- 읽기: **본인만**("내 기록" 함수). 다른 팀원의 횟수는 1차에서 보여주지 않는다(순위 화면 없음). 쓰기: 서버만(예약 작업). 앱 직접 쓰기 권한 없음.

### 7-4. 월간 출석 수 `monthly_attendance` (v4 신설)

**무엇을 저장하나:** 팀별·사람별 월간 출석 횟수(숫자만). 2차 팀 구독 리포트(월별 참석 인원·개인 출석률) 재료 `[결정됨 Q-058 4번]`. 이 표가 없으면 2차 리포트는 최근 10경기 범위만 가능하다.

| 이름 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| team_id | ID | 필수 | |
| user_id | ID | 필수 | 회원 탈퇴 시 같이 삭제 |
| month | 날짜 | 필수 | 그 달 1일(경기 시작일 기준, 한국 시간) |
| attendance_count | 숫자 | 필수 | 그 달 출석 횟수 |

- (팀, 사람, 월) 조합당 한 줄. 경기 종료 처리(7-1)에서 함께 +1.
- 월별 참석 인원(팀 전체)은 이 표를 합산해서 구한다(따로 저장하지 않음). 회원 탈퇴한 사람 몫은 지난 달 숫자에서도 빠진다.
- 개인 출석률의 분모(그 달 경기 수)는 7-6 `team_monthly_matches`에 따로 남긴다 `[결정됨 Q-061 5번]`.
- 팀을 떠난 사람의 줄은 **남긴다** `[결정됨 Q-061 2번]` ( 2차 리포트에서 개인별 목록은 현재 팀원만 이름과 함께 보이고, 떠난 사람 몫은 월별 합계에만 들어감).
- 읽기: 1차에는 **아무도 직접 읽지 않음**. 2차에 팀 리포트 서버 함수가 이용 권한(10장)을 확인한 뒤 관리자에게 준다. 쓰기: 서버만.

### 7-5. 최근 10경기 보관과 자동 삭제 (v4 신설)

**규칙** `[결정됨 Q-058 1번]`: 팀마다 최근 10경기의 상세 기록만 보관하고, 11번째 이전 경기는 서버 예약 작업이 자동으로 지운다.

- **"10경기"로 세는 것** `[결정됨 Q-061 1번]`: 경기 종료 시각이 지났고 **취소되지 않은** 일정을 최근 순으로 10개 센다(배치를 확정하지 않아 투표가 없었던 경기도 셈). 다가오는 일정은 세지 않고 지우지 않는다. 취소된 일정은 세지 않으며, 남은 10경기 중 가장 오래된 경기보다 이전 것이면 함께 지운다.
- **지우는 조건**: 11번째 이전이면서 (a) 경기 종료 처리(출석·카운트 반영)가 끝났고 (b) 투표가 있었다면 마감 처리(1위·카운트 반영)도 끝난 경기만. 카운트 반영 전에는 절대 지우지 않는다.
- **실행 시점**: 투표 마감 처리 직후, 그리고 하루 1회 예약 작업. 경기 단위로 한 번에 지운다(일부만 남는 일 없음).
- **경기 줄(`matches`)을 지우면 함께 지워지는 것**(같이 삭제): 참석 응답(`attendance_responses`), 게스트(`match_guests`)와 게스트 실력 등급(`skill_ratings`의 guest_id 줄), 배치(`lineups`)·팀 블록·배치 명단·변경 이력, 투표 회차(`award_polls`)·투표 대상자·투표 참여 표시·득표 집계·수상자, 출석 기록(`attendance_records`).
- **지워지지 않는 것**: 시즌별 카운트(7-3), 월간 출석 수(7-4), 부상 기록(`injuries.return_check_sent_for`만 비움), 알림함(이동 대상이 외래 키가 아니므로 남고, 눌러도 이동하지 않음. 30일 뒤 정리).
- 데이터베이스 삭제 동작: 위 표들의 `match_id`(또는 `lineup_id`, `guest_id`)는 모두 같이 삭제(`ON DELETE CASCADE`)로 만든다. `injuries.return_check_sent_for`는 비움.
- **팀 해체 때** 남은 최근 10경기 상세 기록을 위와 같은 방식으로 모두 지운다 `[결정됨 Q-061 4번]`. 시즌별 카운트·월간 숫자(7-3, 7-4, 7-6, 7-7)는 남는다.

### 7-6. 팀별 월간 경기 수 `team_monthly_matches` (v4.1 신설)

**무엇을 저장하나:** 팀별로 그 달에 열린 경기 수(숫자만). 2차 "개인 출석률"(출석 수 ÷ 그 달 경기 수)의 분모 `[결정됨 Q-061 5번]`. 경기 기록이 지워져도 남는다.

### 7-7. 참석 투표 참여율 `monthly_vote_participation` (v4.1, `[결정됨 Q-062]`, v4.2 저장 방식 3번 결정됨)

## 8. 동의와 부상

**동의 받는 방식** `[결정됨 Q-028, Q-049, Q-053, Q-057]`: 가입 단계(2-2)에서 만 14세 확인·이용약관·개인정보 수집·이용(필수)과 **부상 정보 수집·이용(선택)**을 받는다. 부상 동의는 다른 동의와 분리된 체크박스이고, 하지 않아도 가입된다(부상 기록 기능만 쓸 수 없음). 문구는 docs/consent-texts.md(kopn 확인 2026-11-05).
부상 기록을 등록할 때마다 동의를 다시 묻지 않고, 서버가 "유효한(철회되지 않은) 부상 동의가 있는가"만 확인한다. 동의가 없으면 앱은 부상 등록 전에 동의 화면을 보여주고, 동의하면 그때 기록을 남긴다.

### 8-1. 동의 기록 `user_consents`

**무엇을 저장하나:** 누가 어떤 동의를, 어느 문구 버전으로, 언제 했는지(그리고 부상 동의는 언제 철회했는지). 지우지 않고 쌓는다(회원 탈퇴 때만 삭제).

| 이름 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| id | ID | 필수 | |
| user_id | ID | 필수 | 회원 탈퇴 시 같이 삭제 `[결정됨 Q-053]` |
| consent_type | 선택(terms, privacy, injury_info) | 필수 | 이용약관 / 개인정보 수집·이용 / 부상 정보 수집·이용. v4에서 `terms`·`privacy` 추가 `[결정됨 Q-053]` |
| consent_version | 글자 | 필수 | 동의한 문구 버전(예: `injury_info-2026-11-05`). 문구가 바뀌면 버전 값을 새로 정한다 |
| agreed_at | 날짜·시간 | 필수 | 서버 시계로 기록 |
| withdrawn_at | 날짜·시간 | 선택 | 철회 시각. **`injury_info`만 철회 가능** `[결정됨 Q-052]`. 약관·개인정보 동의는 철회 대신 회원 탈퇴 |

- 만들기(서버 함수로만):
  - 가입 단계 함수가 `terms`·`privacy`(필수, 없으면 가입 거절)와 `injury_info`(체크했을 때만)를 함께 만든다.
  - **나중에 부상 동의** `[결정됨 Q-049]`: 가입 때 하지 않았거나 철회한 사람이 다시 동의하면 새 줄을 만든다(이전 줄은 그대로).
- **부상 동의 철회** `[결정됨 Q-052]`: 프로필 설정에서 언제든 철회. 서버 함수 하나가 한 번에 (1) 유효한 `injury_info` 줄에 `withdrawn_at`을 찍고 (2) 그 사람의 **부상 기록 전부(진행 중·지난 기록)와 변경 이력을 삭제**한다. 즉시 팀원에게 안 보인다. 철회 뒤 다시 동의해도 지운 기록은 돌아오지 않는다.
- 동의 기록 줄 자체는 철회 후에도 남긴다(언제 동의하고 언제 철회했는지의 기록). 회원 탈퇴 때 함께 삭제한다.
- 읽기: 본인만. 수정·삭제 불가(철회 표시는 철회 함수만).
- 약관·처리방침 문구가 개정될 때 다시 동의를 받을지는 출시 전 처리방침 작성 때 정한다(표 구조는 새 줄 추가로 충분).
- 만 14세 확인은 이 표가 아니라 `profiles.age_14_confirmed_at`에 둔다(가입 필수 조건이라 프로필과 같이 있어야 함).
- (v4.2) 동의 기록은 로그인 방법이 아니라 **계정 기준**이다. 인증된 같은 이메일로 새 로그인 방법이 기존 계정에 붙어도 동의를 다시 받지 않고 새 줄도 만들지 않는다 `[결정됨 Q-063]`.

### 8-2. 부상 기록 `injuries`

**무엇을 저장하나:** 본인이 등록한 부상 한 건(예상 회복 기간, 메모). 소속된 모든 팀의 부상자 라인업에 보인다.
**보관** `[결정됨 Q-058 6번]`: 진행 중인 것과 지난(회복된) 기록 모두 **동의 철회 또는 회원 탈퇴 전까지** 보관한다. 부상은 사람 기준 기록이라 팀을 떠나거나 경기 기록이 지워져도(7-5) 영향이 없다. 쓰임: 팀 부상 인원 표시 + 2차 운영진 팀 리포트(동의 문구에 명시, Q-057).

| 이름 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| id | ID | 필수 | |
| user_id | ID | 필수 | 한 사람당 진행 중 부상은 1건. 탈퇴 시 같이 삭제 |
| started_on | 날짜 | 필수 | 등록일 |
| expected_return_on | 날짜 | 필수 | 예상 복귀일. "남은 W"는 오늘 기준으로 화면에서 계산 |
| memo | 글자 | 선택 | 20자 이내(보이는 글자 단위) |
| status | 선택(active, recovered) | 필수 | 부상 중 / 회복 |
| recovered_at | 날짜·시간 | 선택 | |
| return_check_sent_for | ID | 선택 | 복귀 확인 알림을 보낸 마지막 일정 (중복 발송 방지). 일정 삭제 시 비움(7-5 자동 삭제 포함) |

- **저장 조건(서버가 확인): 본인에게 철회되지 않은 `injury_info` 동의 기록이 있을 때만 등록 가능** `[결정됨 Q-028, Q-049]`. 없으면 등록 거절.
- 0W가 지나도 자동 해제하지 않는다. 0W 이후 참석 투표가 열리면 복귀 확인 알림. "아직 회복 중"이면 +1W/+2W 연장.
- 읽기(1차): 본인 + 본인과 같은 팀에 현재 소속된 사람(메모 포함, 진행 중인 것만). 회복된 지난 기록은 본인만. 2차 운영진 팀 리포트는 서버 함수가 이용 권한(10장)을 확인해 관리자에게 준다(동의 문구 "팀 리포트는 팀장·운영진").
  - 팀원 읽기 규칙 자체에 "주인의 부상 동의가 유효(철회 안 됨)"를 매번 확인하는 조건을 넣는다(S-07). 동의 기록은 본인만 읽으므로 확인은 SECURITY DEFINER 확인 함수로 한다. 철회 함수가 기록을 바로 지우지만, 지우기 전 순간에도 안 보이게 하는 이중 장치다.
- 쓰기: 본인(서버 함수로). 삭제: 동의 철회 함수·회원 탈퇴만.

## 9. 알림

모든 알림은 **푸시 + 앱 안 알림함** 둘 다로 간다 `[결정됨 Q-027 M-20]`.
**조용한 시간(00:00~08:00)에도 알림함에는 바로 쌓고, 푸시만 13:00에 보낸다** `[결정됨 Q-033, 시각은 Q-071 11번으로 08:00→13:00]`. 새 팀원 합류 알림은 푸시 없이 알림함에만 `[결정됨 Q-071 9번]`.

알림 종류(`kind`) 목록 = docs/notifications.md 목록 + Q-022 추가 4종:
`match_created`(일정 생성·참석 투표 오픈), `rsvp_deadline_soon`, `waitlist_promoted`, `match_cancelled`, `lineup_confirmed`, `lineup_changed`, `award_poll_opened`, `award_deadline_soon`, `join_request_received`, `join_request_decided`, `member_left`, `team_dissolved`, `injury_return_check`, **`manager_assigned`, `manager_unassigned`, `ownership_received`, `member_removed`** (Q-022), (2차) `monthly_report`.

### 9-1. 알림 발송 대기열 `notification_outbox`

**무엇을 저장하나:** 보낼 푸시와 보낼 시각. 조용한 시간(00:00~08:00)에 걸리면 13:00으로 미루고(Q-071 11번), 예외 규칙(POM 오픈 즉시, 미투표 알림 처리 Q-072 1번)은 서버가 계산한다. 마감 2시간 전 알림 앞당김은 폐지(Q-071 8번). 알림함 줄(9-2)은 이와 상관없이 바로 만든다.

| 이름 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| id | ID | 필수 | |
| notification_id | ID | 필수 | 알림함 줄(9-2). 알림함 줄 삭제 시 같이 삭제 |
| user_id | ID | 필수 | 받는 사람. 탈퇴 시 같이 삭제 |

| status | 선택(pending, sent, skipped, failed) | 필수 | |
| sent_at | 날짜·시간 | 선택 | |

- 푸시 문구는 알림함 줄의 내용을 쓴다(같은 알림이 두 곳에서 다르게 보이지 않게).
- 같은 알림 중복 방지는 알림함 쪽에서 한다.
- 읽기·쓰기: 서버만. 발송 후 30일 지나면 삭제(S-18 권고).

### 9-2. 알림함 `notifications` `[결정됨 Q-027 M-20]`

**무엇을 저장하나:** 앱 안 알림함에 보이는 알림 한 건과 읽음 여부.

| 이름 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| id | ID | 필수 | 무작위 번호 (Realtime 등록 대비) |
| user_id | ID | 필수 | 받는 사람. 탈퇴 시 같이 삭제 |
| kind | 선택(위 목록) | 필수 | 알림 종류 |
| team_id | ID | 선택 | 관련 팀. 팀 줄이 지워질 일은 없음(해체는 표시만) |
| ref_type / ref_id | 글자 / ID | 선택 | 누르면 이동할 대상(일정·가입 신청·배치 등). 외래 키 아님 |
| actor_id | ID | 선택 | **문구에 이름이 들어간 다른 사람**(예: 가입 신청자, 팀 탈퇴한 팀원). **탈퇴 시 같이 삭제** → 그 사람이 회원 탈퇴하면 이 알림이 사라짐 `[결정됨 Q-044]` |
| title / body | 글자 | 필수 | 보낸 시점의 문구(매니저 말투). **다른 사람 이름을 넣는다** `[결정됨 Q-044]`. 실력 등급·득표수·부상 메모·초대 코드는 넣지 않는다 |
| dedupe_key | 글자 | 필수 | 같은 알림 중복 방지 (받는 사람, 종류, 관련 대상) 조합 고유 |
| created_at | 날짜·시간 | 필수 | 알림이 생긴 시각 = 알림함에 보이는 시각 |

- v2의 `visible_at` 칸은 삭제했다(알림함은 바로 쌓으므로 필요 없음 `[결정됨 Q-033]`).
- **이름 규칙**: 다른 사람 이름을 문구에 넣는 알림은 반드시 그 사람을 `actor_id`에 적는다. 한 알림에는 다른 사람 이름을 한 명까지만 넣는다(그래야 탈퇴 시 정확히 지울 수 있음). 팀만 떠나고 회원 탈퇴하지 않은 사람의 이름은 알림함에 남는다.
- **보관 30일** `[결정됨 Q-041]`: `created_at`부터 30일이 지나면 서버 예약 작업이 삭제한다(읽음 여부와 무관).
- **떠난 팀의 알림** `[결정됨 Q-041]`: 지우지 않고 남긴다. 누르면 이동하지 않는다 — 앱은 `team_id`가 지금 소속된 팀이 아니면 이동하지 않고, 서버는 원래 권한 규칙대로 대상 데이터를 주지 않는다. 대상이 없어졌을 때도 이동하지 않는다.
- **읽기: 본인만**(`user_id = 본인`).
- **쓰기: 본인은 `read_at`만** 고칠 수 있다(칸 단위 권한, 읽음 표시·모두 읽음). 비우기(안 읽음으로 되돌리기) 허용 여부는 화면 작업 때 확인. 만들기는 서버만. 본인이 삭제할 수 있게 할지는 화면 작업 때 확인(초안: 불가).
- 안 읽음 개수 표시에 Realtime을 쓸 수 있다. 등록한다면 기본 키가 무작위 `id` 하나뿐이라 11장 7번 조건을 만족한다(출시 전 security 점검 대상).

## 10. 2차 대비: 이용 권한 (entitlements)

### 10-1. 이용 권한 `entitlements`

**무엇을 저장하나:** 누가(또는 어느 팀이) 어떤 유료 등급을 언제까지 쓸 수 있는지. **1차에는 표만 있고 비어 있다.** 결제 정보 자체(영수증, 카드 등)는 저장하지 않는다.

| 이름 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| id | ID | 필수 | |
| subject | 선택(user, team) | 필수 | 개인 구독이면 사람, 팀 구독이면 팀 |
| user_id | ID | 둘 중 하나 | 탈퇴 시 같이 삭제 |
| team_id | ID | 둘 중 하나 | |
| plan | 선택(personal_plan, team_plan) | 필수 | |
| starts_at / ends_at | 날짜·시간 | 필수 | 유효 기간 |
| source | 글자 | 필수 | 어디서 받았나(2차에서 결정) |

- 읽기: 본인 것 + 팀 구독은 그 팀 관리자. 쓰기: 서버만.
- 보상형 광고(광고 1회 = 경기 1건 본인 득표수 보기) 기록 표 `ad_unlocks`는 2차에 추가한다(1차 생성 안 함).

### 10-2. 판단은 한 곳에서

- **앱:** `app/lib/core/entitlements/` 한 곳에서 "이 사람이 이 정보를 볼 수 있나"를 판단한다. 화면은 이 결과로만 버튼을 숨기거나 보여준다. 1차에는 항상 "무료 등급"을 돌려준다(득표수 보기·리포트 메뉴 숨김).
  - 예: `canViewOwnVoteCount(match, category)`, `canViewTopThree(match, category)`, `canViewTeamReport(team)`, `showAds()`
- **서버:** 숫자를 실제로 내주는 서버 함수(`get_vote_counts`, `get_team_report`)가 이용 권한 표를 다시 확인한다. 1차에는 이 함수들이 1위 외에는 아무것도 돌려주지 않는다. 앱 판단만 믿지 않는다.
- 2차 팀 리포트의 출석은 확정 배치 기준 출석만 쓴다(노쇼 구분 없음, Q-043). 최근 10경기 이전은 월간 출석 수(7-4)만 있다.
- (v4) 2차 "본인 득표수 보기"(광고 시청·개인 구독)는 **득표 집계가 남아 있는 최근 10경기**에서만 가능하다(Q-058). 엔타이틀먼트 판단(`canViewOwnVoteCount`)은 권한만 보고, 경기가 지워졌으면 서버 함수가 "기록 없음"을 돌려준다.

## 11. 데이터베이스 공통 규칙 (마이그레이션 작성 기준)

승인 후 builder가 따를 기준. 승인 전에는 마이그레이션을 만들지 않는다. Supabase 프로젝트는 서울 리전 `[결정됨 Q-024]`.

1. 모든 표에 권한 규칙(RLS)을 켠다. 규칙이 없는 표 = 아무도 못 읽는 표.
2. "그 팀 팀원인가 / 관리자인가 / 팀장인가"는 공용 확인 함수 3개로만 판단한다(`is_team_member`, `is_team_staff`, `is_team_owner`). 해체된 팀은 모두 거짓.
3. 규칙 검사가 필요한 변경(프로필 만들기·가입 동의, 부상 동의 추가·철회, 가입 신청·승인, 역할 변경, 참석 투표, POM 투표, 배치 확정·확정 후 수정, 로고 글자 변경, 부상 등록, 기기 주소 등록, 회원 탈퇴)은 서버 함수로만 하고, 앱이 표에 직접 쓰는 권한을 주지 않는다.
4. 서버 함수는 검색 경로를 고정하고, 호출자 확인(`auth.uid()`)을 함수 첫 줄에서 한다.
   - (security 반영) `SECURITY DEFINER` 함수는 모두 `SET search_path = ''`로 고정하고, 함수 안의 표·함수 이름은 `public.teams`, `auth.uid()`처럼 스키마까지 적는다.
   - (security 반영) `auth.uid()`가 비어 있으면(로그인 안 됨) 즉시 거절한다.
   - (security 반영) Postgres는 새 함수의 실행 권한을 기본으로 모두에게 준다. 함수마다 `REVOKE EXECUTE ... FROM PUBLIC, anon`을 하고 필요한 역할(`authenticated`)에만 다시 준다.
   - (security 반영) 공용 확인 함수(`is_team_member` 등)는 `team_id`만 받고 사람은 항상 `auth.uid()`로 판단한다. API에 노출되지 않는 별도 스키마(예: `private`)에 둔다. 소속 상태 `active` + 팀 `dissolved_at` 없음을 함께 확인한다.
   - (security 반영) 예약 작업 전용 함수(일정 자동 생성, 경기 종료 처리(출석·카운트), 투표 마감·1위 선정·수상 카운트, 최근 10경기 정리, 프로필 없는 로그인 계정 정리, 알림 발송·30일 정리)는 `authenticated`·`anon`에게 실행 권한을 주지 않는다.
   - (v2) 프로필이 없는 호출자는 프로필 만들기 함수 외 모든 서버 함수에서 거절한다(Q-010). (v4.2: 같은 이메일 확인 함수는 Q-063으로 폐지)
5. 서비스 키는 서버 예약 작업과 서버 함수 실행 환경에만 둔다. 회원 탈퇴(계정 삭제), 외부 로그인 연결 끊기·토큰 철회처럼 관리자 권한이 필요한 처리는 서버 함수 실행 환경에서만 한다. 카카오 Admin 키·애플 키도 서버 비밀값에만 둔다.
6. 마이그레이션 파일 하나 = 변경 하나. 파일 이름은 `YYYYMMDDHHMM_설명.sql`. 승인본과 다른 표·칸을 만들지 않는다.
7. 실시간 변경 알림(Realtime)에는 공개해도 되는 표만 등록한다(득표 집계·투표 참여 표시·실력 등급 제외).
   - (security 반영) Realtime의 삭제(DELETE) 알림은 권한 규칙(RLS)이 걸러주지 않고 기본 키를 모든 구독자에게 보낸다. 등록하는 표는 기본 키가 무작위 `id` 하나뿐이어야 하고, 가능하면 줄을 지우지 않고 상태만 바꾼다. 게시(publication)는 표 이름을 하나씩 등록하고 "모든 표"로 만들지 않는다.
   - (v2) 회원 탈퇴는 여러 표의 줄을 실제로 지운다. Realtime에 등록한 표에서 탈퇴로 줄이 지워지면 무작위 `id`만 나가므로 위 조건을 지키면 문제없다. (v3) 알림함 30일 정리도 같다.
8. (security 추가) 뷰(view)를 만들면 반드시 `security_invoker = true`를 붙인다. 실력 등급·득표 집계·투표 참여 표시를 읽는 뷰는 만들지 않는다.
9. (security 추가) 앱이 직접 쓰기를 허용하는 표는 (a) 수정 가능한 칸을 칸 단위 권한으로 제한하고, (b) `WITH CHECK`에서 바뀐 뒤의 `team_id`·`match_id`도 관리자 권한을 다시 확인하며, (c) `id`, `team_id`, `created_by`, `created_at`, `updated_by`는 앱이 바꾸거나 지정하지 못하게 한다(`updated_by`·`updated_at`은 트리거가 채움).
10. (security 추가) 권한 판단에 로그인 계정의 `user_metadata`(사용자가 직접 고칠 수 있음)를 쓰지 않는다. 카카오·구글·애플이 넘겨준 이름·사진을 프로필에 자동 복사하지 않는다.
11. (security 추가) 기본 키는 무작위 uuid(`gen_random_uuid()`, v4)를 쓴다. 시간 순서 uuid(v7)는 배치 명단·투표 관련 표에 쓰지 않는다.
12. (security 추가) 함수 안에서 `RAISE NOTICE`/로그로 투표 후보·초대 코드 값·FCM 토큰·부상 메모를 남기지 않는다.
13. (v2) **사람 칸의 삭제 동작**: 사람을 가리키는 모든 칸은 2-5 표대로 `ON DELETE CASCADE`(같이 삭제) 또는 `ON DELETE SET NULL`(비움)을 반드시 적는다. 삭제 동작을 적지 않은 사람 칸은 만들지 않는다(적지 않으면 회원 탈퇴가 막힘). "비움"인 칸은 필수(NOT NULL)로 만들 수 없다.
14. (v2, v3·v4 보강) **글자 수·이름 검사** `[결정됨 Q-012, Q-034, Q-048]`: 정확한 "보이는 글자" 수는 앱(Flutter `characters`)이 센다. Postgres는 보이는 글자 단위로 셀 수 없으므로, 데이터베이스(또는 서버 함수)는 (a) 앞뒤 공백 없음, (b) 줄바꿈·제어 문자 없음, (c) 비어 있지 않음, (d) 코드 포인트 수 상한 = 글자 상한 × 8(이모지 조합 여유, 예: 팀 이름 80, 팀에서 쓸 이름 64, 자기소개·부상 메모 160)을 검사한다. **이름(팀 이름·팀에서 쓸 이름·게스트 이름)은 (e) 가운데 공백이 두 개 이상 이어지지 않음, (f) 보이지 않는 문자 없음**도 검사한다. 이모지·특수문자는 막지 않는다.
    - **보이지 않는 문자** `[결정됨 Q-048]`: 앱과 서버가 **같은 목록**으로 저장 전에 지운다(서버 함수가 지운 뒤 저장, 데이터베이스 검사는 남아 있으면 거절). 목록: 폭 없는 공백(U+200B), 폭 없는 비결합자(U+200C), 단어 결합자(U+2060), BOM(U+FEFF), 소프트 하이픈(U+00AD), 결합 그래핌 결합자(U+034F), 몽골 모음 구분자(U+180E), 방향 제어 문자(U+200E·U+200F·U+202A~U+202E·U+2066~U+2069), 한글 채움 문자(U+3164·U+115F·U+1160·U+FFA0). 지운 결과가 비면 "이름을 입력해주세요"로 거절(1자 이상 규칙).
    - **이모지에 쓰이는 보이지 않는 문자**(폭 없는 결합자 U+200D, 변형 선택자 U+FE0E·U+FE0F)는 지우면 가족·국기 같은 이모지가 깨진다(Q-034 이모지 허용과 충돌). 이모지 사이에 있을 때만 남기고 그 밖에서는 지운다 `[lead 정리 M-38, decisions.md]`(이 판단은 Postgres로 어려워 서버 함수(Edge Function)에서 처리).
    - 그 밖의 공백 문자(전각 공백 등)는 일반 공백으로 바꾼 뒤 앞뒤 공백 제거·연속 공백 규칙을 적용한다.
    - 앱은 저장 전에 앞뒤 공백을 지우고 가운데 연속 공백을 하나로 줄인다. 즉 앱을 조작하면 상한을 조금 넘길 수는 있어도 무한히 긴 값은 막힌다. 더 엄격히 하려면 서버 함수(Edge Function, `Intl.Segmenter`)에서 세는 방법이 있다(구현 단계 판단).
15. (v3, v4·v4.2 수정) **로그인 설정** `[결정됨 Q-063 A]`: Supabase 기본 자동 합치기(인증된 같은 이메일이면 같은 계정)를 그대로 쓴다. 수동 연결(manual linking)은 끈다. 앱은 계정 연결·연결 해제 기능을 만들지 않는다. 쓰지 않는 로그인 방식(특히 **Email**·전화번호 등 카카오·구글·애플 외 방식)은 Supabase 대시보드에서 끈다(개발 프로젝트는 2026-11-05 꺼짐 확인, 운영 프로젝트도 출시 전 확인). 권한 판단에 로그인 방법 종류나 공급자가 넘긴 이메일을 쓰지 않는다(사람은 `auth.uid()`로만 판단). v4의 "같은 이메일 확인 함수"(S-12)는 폐지.

### 13-2. 상세

**S-01 (높음, 확인 필요) 같은 이메일 계정 자동 연결 — M-07**
- Supabase 공식 문서(Identity Linking)에 따르면 OAuth로 로그인할 때 **같은 이메일의 기존 사용자가 있으면 새 로그인 수단을 그 사용자에 자동으로 연결**하며, 이 기능은 "모든 사용자의 이메일이 고유하다"는 전제로 동작한다. 문서에는 **자동 연결을 끄는 설정이 나와 있지 않다**(2026-11-04 확인 시점). 끌 수 있는지 = **확인 필요**.
- 끌 수 없다면 security.md "이메일이 같다는 이유만으로 계정이 자동 병합되지 않는다"를 **지킬 수 없다**. 또 같은 이메일 계정 두 개가 공존할 수 없으므로 기획서의 "중복 가입 안내" 기능도 같은 이메일인 경우에는 발동할 상황 자체가 없어진다.
- 추가 확인 필요: Supabase 카카오 로그인이 카카오 이메일의 "인증됨" 여부를 어떻게 넘기는지. 인증되지 않은 이메일로도 자동 연결된다면 계정 탈취(미리 남의 이메일로 가입해 두기) 경로가 된다.
- 수동 연결(`linkIdentity`, 로그인된 본인만)은 프로젝트 설정에서 manual linking을 켜야 쓸 수 있다(문서상 베타). 계정 연결 기능의 전제 조건이다.
- 권고: Supabase 테스트 프로젝트에서 (1) 구글·카카오를 같은 이메일로 차례로 로그인했을 때 실제 병합 여부, (2) 자동 연결을 끄는 설정 유무, (3) 카카오 미인증 이메일 처리를 확인한다. 끌 수 없으면 lead가 kopn에게 "체크리스트를 '인증된 이메일만 자동 연결 허용'으로 바꿀지"를 물어야 한다. **확인과 결정 전에는 승인 불가.**
- (v4.2 architect 표시) 결정됨: Q-063 A로 "인증된 같은 이메일이면 같은 계정"을 택했고 security.md 체크리스트도 그에 맞게 바꿨다. 위 권고 (3) 카카오 미인증 이메일 처리는 여전히 `[확인 필요]`(12-4).

**S-02 (중간) 투표 익명성 잔여 경로**
앱 사용자 경로는 막혀 있다: 투표 참여 표시는 본인 것만, 득표 집계는 누구도 직접 못 읽음, 둘 다 Realtime 제외, 득표 집계에 시각 칸 없음. 남은 경로는 운영자(데이터베이스 최고 권한) 수준이다.
- 한 표를 한 트랜잭션에서 쓰므로, 투표 참여 표시 줄과 득표 집계 줄의 **트랜잭션 번호(`xmin`)가 같다.** 득표 집계 줄은 갱신될 때마다 바뀌어 마지막 투표자만 맞춰볼 수 있지만, 정리되기 전의 옛 줄(dead tuple), 변경 로그(WAL), 시점 복구용 백업에는 전체 순서가 남는다.
- Supabase 로그(API 요청 로그, Postgres 오류 로그)에 투표 함수의 인자(후보)가 남는지 = **확인 필요**. 요청은 반드시 POST 본문으로 보내고 URL 쿼리에 후보를 넣지 않는다.
- 권고: (1) 6장의 "개발자 누구도" 문구를 정확하게 수정함(반영). (2) 투표 마감 처리 때 해당 경기의 투표 참여 표시·득표 집계 줄을 한 트랜잭션에서 다시 써서 트랜잭션 번호를 같게 만들고, 이후 자동 정리(vacuum)로 옛 줄이 사라지게 한다. (3) pgaudit 같은 문장 감사 기록을 켜지 않는다. (4) 득표 집계 줄 미리 만들기, 투표 함수가 득표수를 돌려주지 않기, 기기·분석 도구에 투표 대상 남기지 않기(6-4 반영). (5) 2차 득표수 조회 함수는 **투표 마감 후에만** 숫자를 돌려준다(진행 중 여러 번 조회하면 단톡방의 "방금 투표했어" 같은 정보와 맞춰 추정 가능).
- 투표 서버 함수가 확인할 것: 호출자가 투표 대상자인지, 후보가 투표 대상자인지, 후보 ≠ 본인, 서버 시각 기준 투표 기간 내인지, 참여 표시 고유 조건으로 중복 차단(실패 시 전체 취소).

**S-03 (중간, 반영) 직접 쓰기 표의 우회**
- 초안의 `teams`는 "쓰기: 관리자"인데 칸 제한이 없어, 운영진이 `dissolved_at`을 직접 써서 팀장 전용인 해체를 하거나 해체를 되돌릴 수 있었다. `created_by` 위조도 가능 → 3-1 반영.
- `pairing_rules`는 "모순 검사는 서버 함수"인데 쓰기가 직접 허용이라 검사를 건너뛸 수 있었다 → 3-7에 서버 함수로만 명확화.
- `match_guests`, `skill_ratings`, `team_settings`, `lineups` 등 직접 쓰기 표는 `WITH CHECK`에서 바뀐 `team_id`를 다시 확인하지 않으면 자기 팀 줄을 다른 팀으로 옮길 수 있다 → 11장 9번 반영.

**S-04 (중간, 반영) SECURITY DEFINER 함수**
- 검색 경로 `''` 고정 + 스키마 명시, 로그인 안 된 호출 거절, `PUBLIC`·`anon` 실행 권한 회수, 공용 확인 함수는 `team_id`만 받기, API 비노출 스키마, 예약 작업 전용 함수 실행 권한 차단을 11장 4번에 반영.
- 공용 확인 함수가 `user_id`를 인자로 받으면 아무나 "이 사람이 이 팀 소속인가"를 물어볼 수 있는 조회 통로가 된다.

**S-05 (중간, 반영) 뷰** — Postgres 뷰는 기본이 만든 사람 권한이라 RLS가 적용되지 않고, Supabase는 `public` 스키마 뷰를 API로 노출한다. 11장 8번 반영.

**S-06 (중간, 반영) Realtime 삭제 알림** — Supabase 문서상 Realtime의 DELETE 이벤트는 RLS로 거를 수 없어 기본 키가 그 표의 구독자에게 간다. `attendance_responses`처럼 (경기, 사람) 묶음 키인 표를 등록하고 줄을 지우면 다른 팀 구독자에게 "이 경기에 이 사람"이 새어 나간다. 11장 7번 반영. Realtime 등록 표 목록은 구현 단계에서 security가 다시 본다.

**S-07 (중간) 부상 공개와 동의 철회**
- 팀원 읽기 규칙이 "등록할 때 동의가 있었다"만 보면 공개 동의를 철회해도 계속 보인다. **팀원 읽기 규칙 자체에** "주인의 두 동의가 모두 유효(철회 안 됨)"를 매번 확인하는 조건을 넣어야 한다(`user_consents`는 본인만 읽으므로 SECURITY DEFINER 확인 함수 필요).
- 동의 문구 버전이 바뀌면 재동의 전까지 비공개로 할지 = 정책 판단.
- 건강 정보는 개인정보보호법상 민감정보로 보인다(별도 동의 필요). 저장 시 추가 보호(암호화 등) 수준, 철회 시 삭제 범위(M-15)는 정책 판단.
- 알림 문구(복귀 확인)에는 부상 메모를 넣지 않는다(9장에 이미 있음). 잠금 화면 미리보기 문구도 문구 결정 시 고려.

**S-08 (중간) FCM 토큰 이전**
- 토큰은 전체에서 중복 금지인데 쓰기는 본인만이다. A가 로그아웃 없이(앱 삭제, 세션 만료) 기기를 넘기거나 같은 기기에서 B가 로그인하면 토큰 줄이 A 소유로 남아 **A의 알림(팀 이름, 일정, 가입 승인 등)이 B가 쓰는 기기로 간다.**
- 권고: 토큰 등록을 서버 함수로 하고, 같은 토큰이 다른 사람 소유면 현재 호출자에게 소유를 옮긴다. 로그인할 때마다 등록, 로그아웃 시 삭제, FCM이 "등록되지 않은 토큰"으로 응답하면 삭제.

**S-09 (중간) 확정 후 배치 수정** — 확정 후 수정은 "변경 이력 + 참석자 알림"이 규칙인데, 관리자가 `lineup_slots`를 직접 고칠 수 있으면 이력·알림을 건너뛴다. 권고: `status = confirmed`인 배치의 블록·명단은 직접 쓰기 금지, 서버 함수로만 수정(이력·버전·알림을 한 번에). 작성 중(draft)만 직접 쓰기 허용. `lineup_change_logs`의 before/after에는 사람 ID만 넣고 이름은 넣지 않는다(탈퇴 시 익명화 가능하도록).

**S-10 (중간) 로고 사진 저장소**
- 팀 검색·초대 확인 화면에서 팀원이 아닌 사람도 로고를 봐야 하므로 (A) 공개 읽기 저장소 + 추측 불가 파일 경로(`team_id/무작위값.jpg`) 또는 (B) 비공개 저장소 + 서버 함수가 짧은 유효기간의 서명 URL 발급 중 택일. 로고는 민감도가 낮아 A로 충분하다고 보지만, 공개 저장소는 삭제 후에도 CDN 캐시에 잠시 남는다.
- 어느 쪽이든: 파일 목록 조회(`storage.objects` SELECT)는 비팀원에게 열지 않음, 올리기·지우기는 경로 첫 폴더의 `team_id`로 `is_team_staff` 확인, 버킷에 용량 상한(예: 1MB)·형식 제한(jpeg/png/webp, **SVG 금지**).
- 휴대폰 사진에는 촬영 위치(GPS) 정보가 들어 있을 수 있다. 업로드 전 앱에서 다시 인코딩해 메타데이터를 지운다.
- 로고 교체 시 이전 파일 삭제, 팀 해체 시 처리(M-01)와 함께 삭제.

**S-11 (중간) 계정 삭제 — M-02**
- 애플 App Store와 구글 Play는 계정을 만들 수 있는 앱에 **앱 안 계정 삭제 기능을 요구**한다(구글은 웹 삭제 요청 경로도). 애플 로그인을 쓰면 삭제 시 애플 토큰 철회도 요구된다. 카카오도 "연결 끊기" 처리 필요. 따라서 M-02는 "할지 말지"가 아니라 "어떻게"의 문제다(세부 요구는 출시 전 다시 확인).
- 구조상 정할 것: `created_by`, `decided_by`, `updated_by`, `changed_by`, `ended_by`, `added_by`, `confirmed_by` 등 계정을 가리키는 칸이 많다. 외래 키 삭제 동작(`ON DELETE SET NULL` 등)을 정하지 않으면 계정 삭제가 막히거나 연쇄 삭제된다. A안(익명 보존)이라면 `award_winners`, `attendance_records`, `award_tallies`, `award_participants`, `lineup_slots`의 `user_id`를 널로 바꿀지 남길지 정해야 한다. ID만 남기고 프로필을 지우는 것은 가명 처리일 뿐, 같은 팀 사람에게는 누구인지 추정 가능하다.
- 삭제 권고 대상: 프로필, 선호 포지션, 부상·부상 이력, 기기 주소, 대기 중 알림, 가입 신청, 투표 참여 표시, 실력 등급, 그룹·라이벌 소속.
- 동의 기록(`user_consents`)을 증빙용으로 일정 기간 보관할지는 정책 판단.

**S-12 (낮음) 중복 가입 안내와 계정 열거**
- 함수가 **인자를 받지 않고** 호출자 본인의 로그인 정보에 있는 이메일만으로 확인하면, 남의 이메일을 넣어 가입 여부를 조회하는 통로가 되지 않는다. 이메일을 인자로 받는 형태는 금지.
- 공급자가 "인증됨"으로 표시한 이메일일 때만 안내한다. 인증 안 된 이메일로도 안내가 뜨면 남의 이메일로 가입 수단을 알아낼 수 있다.
- 반환은 "있음/없음 + 로그인 수단 종류"까지만(초안대로). S-01 결과에 따라 이 기능 자체가 필요 없어질 수 있다.
- (v4.2 architect 표시) Q-063으로 이 기능은 폐지되었다. 위 내용은 기록으로만 남긴다.
- M-05 A안의 "다른 계정에서 사용 중" 안내는 사용자가 그 로그인 수단의 주인임을 이미 인증한 뒤라 열거 문제 아님.

**S-13 (낮음) 초대 링크**
- 32바이트 무작위 값 + SHA-256 해시 저장이면 충분하다(느린 해시 불필요). 대입으로 맞힐 확률이 사실상 0이라 **대입 방지용** 횟수 제한은 필수가 아니다. 다만 가입 신청 남발·서버 부하 방지를 위해 초대 확인·가입 신청 함수에 사람당 가벼운 호출 제한을 권고.
- 구현 주의: `timestamptz + interval`은 Postgres에서 불변(immutable) 연산이 아니어서 생성 칸(generated column)으로 `expires_at`을 만들 수 없다. 트리거로 `created_at = now()`, `expires_at = created_at + 24시간`을 강제하고 두 칸 수정을 막거나, `expires_at`을 저장하지 않고 확인 시 `now() < created_at + interval '24 hours'`로 계산한다(어느 쪽이든 architect 판단).
- 링크가 웹 페이지(앱 미설치 시 스토어 이동)를 거치면 웹 서버 접속 기록에 링크 값이 남는다. 링크 값은 URL의 `#` 뒤(서버로 전송 안 됨)에 두거나 접속 기록에서 제외. Q-002(설치 후 이어서 가입)를 외부 딥링크 서비스로 하면 링크 값이 그 회사로 넘어간다(외부 서비스 추가 → kopn 결정).
- 링크가 새도 할 수 있는 일은 "가입 신청"까지이고 관리자 승인이 필요해 영향은 제한적이다.

**S-14 (낮음) 팀 검색** — 해체 팀 제외·주소/좌표 제외는 3-1에 반영. 추가 권고: 검색어 최소 2자, 결과 상한(예: 20개), `ILIKE` 특수문자(`%`, `_`) 이스케이프, 사람당 호출 제한(전체 팀 목록 긁어가기 방지). 팀 이름 중복 허용(M-04)이면 같은 이름 팀 사칭이 가능하나 가입이 승인제라 영향 낮음.

**S-15 (낮음) 실력 등급 간접 노출**
- 팀 나누기 계산을 관리자 앱에서 하든 서버 함수에서 하든, 저장 결과(배치·경고·변경 이력)와 공유 이미지에 등급·합계가 없으면 된다(초안대로). 공유 이미지 생성 코드는 등급 필드가 없는 화면용 데이터만 받게 한다.
- 관리자가 팀원으로 강등되면 서버 규칙으로 즉시 막히지만, 앱 기기 캐시에 남은 등급 목록도 역할 변경 시 지운다.
- 팀원 목록·내 기록 등 SECURITY DEFINER 함수가 `skill_ratings`를 조인하지 않는지를 코드 리뷰 항목으로 둔다.

**S-16 (낮음, 정책) 소규모 투표 추론** — 투표 대상자가 2명이면 "서로 찍었다"가 확정되고, 3명이면 1위 결과로 상당 부분 추정된다. 2차 "본인 득표수"가 붙으면 더 분명해진다. 구조로 막을 수 없어서, 최소 인원 미만이면 투표를 열지 않을지 등은 정책 판단.

**S-17 (낮음) `cast_on`** — 투표 참여 표시의 날짜 칸은 중복 방지·미투표 알림에 필요 없다. 최소 수집 원칙상 빼는 것을 권고(구조 변경이므로 architect 판단).

**S-18 (낮음) 기타**
- 관리자가 가입 신청자의 프로필·선호 포지션을 읽는 권한은 **대기 중 신청**에만 한정(거절·취소 후에는 불가).
- 게스트 이름은 동의 없이 입력되는 제3자 정보다. 이름(별명 가능)만 받는 현재 구조 유지. 보관 기간은 정책 판단.
- `notification_outbox`는 발송 후 일정 기간(예: 30일)이 지나면 삭제.
- 카카오 로그인 동의 항목은 최소로 요청하고, 공급자 정보를 프로필에 자동 복사하지 않는다(11장 10번).
