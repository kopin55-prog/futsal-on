## 0. 읽는 법 (kopn용)

- **테이블** = 엑셀 시트 하나라고 생각하면 된다. 한 줄(행)이 한 건의 기록이다.
- **필드** = 시트의 열(칸 제목).
- **누가 읽고/쓸 수 있나** = 데이터베이스가 직접 막는 규칙(RLS). 앱 화면에서 숨기는 것과 별개로, 앱을 조작해도 서버가 거절한다.
- **"서버 함수로만"** = 앱이 표에 직접 쓰지 못하고, 서버에 있는 정해진 절차(예: "참석 투표하기")를 통해서만 바뀐다는 뜻. 규칙 검사(마감 시간, 정원, 본인 투표 금지 등)를 서버가 한 번에 처리한다.
- **탈퇴 시** = 회원 탈퇴(계정 삭제)할 때 그 줄이 어떻게 되는지. "같이 삭제"는 줄이 지워지고, "비움"은 줄은 남고 그 칸만 빈칸이 된다. 2-5에 표 전체를 모았다.

타입 표기:

| 표기 | 뜻 |
| --- | --- |
| ID | 자동으로 붙는 추측 불가능한 고유 번호 (uuid) |
| 글자 | 텍스트 |
| 숫자 | 정수 |
| 날짜·시간 | 시각 (시간대 포함으로 저장) |
| 날짜 | 날짜만 |
| 시각 | 하루 중 시각 (예: 10:00) |
| 예/아니오 | 참·거짓 |
| 선택(…) | 정해진 값 중 하나만 |
| 목록(…) | 여러 값 |

역할 줄임말: **팀장**(owner), **운영진**(manager), **팀원**(member). "팀장·운영진"은 이하 **관리자**로 줄여 쓴다.
"그 팀 팀원" = 그 팀에 현재 소속된 사람 전체(팀장·운영진 포함).
"회원 탈퇴" = 앱 계정 삭제. "팀 탈퇴" = 한 팀에서만 나감. 둘을 구분해 쓴다.

## 1. 전체 그림

```
[로그인 계정] 1──1 [프로필] 1──1 [선호 포지션·전문GK]
      │                 │
      │                 ├──* [부상 기록] ──* [부상 변경 이력]
      │                 ├──* [기기 알림 주소]
      │                 └──* [알림함]
      │
      └──* [팀 소속] *──1 [팀(식별코드 포함)] 1──1 [경기 설정]
                │          │
                │          ├──* [실력 등급]  (관리자만)
                │          ├──* [초대 코드] / [가입 신청]
                │          ├──* [그룹·라이벌]
                │          └──* [일정(경기)]
                │                  ├──* [참석 투표] / [게스트]
                │                  ├──1 [팀 배치] ──* [팀 블록] ──* [배치 명단], [노쇼 표시(관리자만)], [변경 이력]
                │                  ├──1 [POM·오늘의 골 투표] → [투표 대상자], [투표 참여 표시], [득표 집계], [수상자]
                │                  └──* [출석 기록]
                └ (2차) [이용 권한(entitlements)]
```

핵심 원칙을 구조로 지키는 방법:

| 원칙 | 구조로 지키는 방법 |
| --- | --- |
| 프로필은 사람당 하나 | 프로필은 로그인 계정과 1:1. 팀별 정보(역할·실력 등급)는 별도 표 |
| 실력 등급은 관리자만 (팀원은 본인 것도 불가, 관리자는 본인 것 포함 조회) | 실력 등급을 팀 소속 표에서 떼어 **별도 표**로 두고, 그 표는 관리자만 읽기 허용 `[결정됨 Q-016]` |
| 누가 누구를 찍었는지 조회 불가 | **"누가 투표했는지"와 "누가 몇 표 받았는지"를 서로 다른 표에 저장하고, 둘을 잇는 정보는 어디에도 저장하지 않음.** 저장 자체를 안 하므로 어떤 경로로도 조회 불가 |
| 득표수 저장, 1차는 1위만 공개 | 득표 집계 표는 앱에서 직접 읽기 금지. 마감 후 서버가 1위만 뽑아 "수상자" 표에 기록, 팀원은 수상자 표만 읽음 |
| 초대 코드 추측 불가·24시간 만료·팀당 1개 | 코드 값은 서버가 만든 무작위 값(32바이트). 원본은 저장하지 않고 지문(해시)만 저장. 만료 시각은 서버 시계로만 정해지고 수정 불가. 팀당 유효한 코드 1개를 데이터베이스가 보장 |
| 노쇼는 관리자만 | 노쇼 표시를 배치 명단에서 떼어 **관리자 전용 표**로 둠 `[결정됨 Q-027 M-10]` |
| 출석·부상 처음부터 저장 | 출석 기록 표, 부상 기록·변경 이력 표를 1차부터 둠 |
| 회원 탈퇴 시 전부 삭제 | 그 사람을 가리키는 모든 칸에 삭제 동작(같이 삭제/비움)을 정해 둠(2-5) `[결정됨 Q-009]` |
| 2차 구독 대비 | "이용 권한" 표와 득표수 조회 서버 함수 자리를 1차부터 둠 (1차는 비어 있음) |

## 2. 계정·프로필

### 2-1. 로그인 계정 (Supabase 제공: `auth.users`, `auth.identities`)

**무엇을 저장하나:** 사람 한 명의 계정과, 그 계정에 연결된 로그인 수단(**카카오·구글**). 연결하면 어느 수단으로 들어와도 같은 계정이 된다. `[결정됨 Q-004]` 1차는 애플 로그인 없음.
Supabase가 기본으로 제공하는 표를 쓰고 우리가 직접 만들지 않는다. 서버는 Supabase **서울 리전** `[결정됨 Q-024]`.

- 로그인 수단 연결은 로그인된 상태에서만 가능(Supabase 기능 그대로 사용).
- 이미 다른 계정에 묶인 로그인 수단을 연결하려 할 때 처리: `[미결 Q-007-2]` (v1 M-05)
- 로그인 수단 연결 해제 허용 여부: `[미결 Q-008-2]` (v1 M-06)
- 이메일이 같은 계정의 자동 연결: `[미결 Q-006-2]` (v1 M-07, security S-01 높음)
- 중복 가입 안내("이전에 카카오로 가입하셨어요")는 새 로그인 직후 서버 함수가 "같은 이메일을 가진 다른 계정이 있는지, 있으면 어떤 로그인 수단인지"만 돌려준다. 계정 ID·이름 등은 돌려주지 않는다. (Q-006-2 결과에 따라 필요 없어질 수 있음)
- 애플 로그인 제외가 iOS 심사에 주는 영향은 `[미결 Q-030]`. 애플이 다시 추가되면 이 절에 로그인 수단만 늘리면 되고 다른 표는 바뀌지 않는다.

### 2-2. 프로필 `profiles`

**무엇을 저장하나:** 사람당 하나뿐인 프로필. 모든 팀에서 같은 이름과 자기소개가 보인다.
**로그인 직후 누구나 프로필부터 만든다** `[결정됨 Q-010]`. 프로필이 없는 계정은 팀 만들기·가입 신청·팀 검색 등 모든 서버 함수에서 거절된다.

| 이름 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| user_id | ID | 필수 | 로그인 계정 번호. 계정당 프로필 1개. **탈퇴 시 같이 삭제** |
| display_name | 글자 | 필수 | 팀에서 쓸 이름(실명 또는 별명). **1~8자, 중복 허용** `[결정됨 Q-011]` |
| bio | 글자 | 선택 | 한줄 자기소개, 20자 이내 |
| age_14_confirmed_at | 날짜·시간 | 필수 | "만 14세 이상입니다" 확인 체크 시각. 체크 없이는 프로필(=가입)을 만들 수 없음 `[결정됨 Q-023]`. 서버 시계로 기록, 수정 불가 |
| created_at | 날짜·시간 | 필수 | 만든 시각 |
| updated_at | 날짜·시간 | 필수 | 마지막 수정 시각 |

- 글자 수는 **눈에 보이는 글자 단위**(이모지 1개 = 1자), 앞뒤 공백 제거 후 셈, 줄바꿈 불가 `[결정됨 Q-012]`. 데이터베이스 검사 방식은 11장 14번.
- v1의 `deleted_at`은 없앴다. 회원 탈퇴 때 줄을 표시만 하지 않고 실제로 지운다(2-5).
- 만들기: 서버 함수로만(만 14세 확인 시각을 서버가 기록하고, 선호 포지션(2-3)도 같이 만듦).
- 읽기: 본인 / 나와 같은 팀에 현재 소속된 사람 / 내 팀에 **대기 중인** 가입 신청을 낸 사람(관리자만, 신청 처리용, S-18).
- 고치기: 본인만. `age_14_confirmed_at`, `user_id`, `created_at`은 고칠 수 없음(칸 단위 권한).

### 2-3. 선호 포지션·전문 골키퍼 `profile_play_prefs`

**무엇을 저장하나:** 팀 나누기에 쓰는 본인 정보(선호 포지션, 전문 골키퍼 여부). 팀원 명단에 보이지 않게 하려고 프로필과 표를 나눴다.

| 이름 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| user_id | ID | 필수 | 프로필 주인. **탈퇴 시 같이 삭제** |
| positions | 목록(골키퍼·수비·중앙·측면·공격) | 필수 | 1~3개, 중복 없음, 순서 없음 |
| is_dedicated_gk | 예/아니오 | 필수 | 전문 골키퍼. 기본 아니오 |
| updated_at | 날짜·시간 | 필수 | 마지막 수정 시각 |

- 저장 규칙(데이터베이스 검사): **전문 골키퍼이면 positions에 골키퍼가 반드시 들어 있어야 한다** `[결정됨 Q-019]`. 앱은 체크하면 골키퍼를 자동 선택한다. 이미 3개를 고른 상태에서 체크할 때 화면 동작은 화면 작업 때 질문(U-09와 함께).
- 쓰기: 본인만 (관리자도 수정 불가).
- 읽기: 본인 + 내가 소속된 팀의 관리자(팀 나누기용) + 대기 중 가입 신청을 받은 팀의 관리자. 일반 팀원은 읽기 불가 `[결정됨 Q-017]`.

### 2-4. 기기 알림 주소 `device_tokens`

**무엇을 저장하나:** 푸시 알림을 보낼 휴대폰 주소(FCM 토큰). 한 사람이 여러 기기를 쓸 수 있다.

| 이름 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| id | ID | 필수 | |
| user_id | ID | 필수 | 주인. **탈퇴 시 같이 삭제** |
| token | 글자 | 필수 | FCM 토큰. 전체에서 중복 없음 |
| platform | 선택(android, ios) | 필수 | |
| updated_at | 날짜·시간 | 필수 | 마지막 갱신 |

- 등록: **서버 함수로만**. 같은 토큰이 다른 사람 소유로 남아 있으면 현재 호출자에게 소유를 옮긴다(S-08 권고 채택). 로그인할 때마다 등록.
- 읽기: 본인만. 삭제: 본인(로그아웃 시) + 서버(FCM이 "등록되지 않은 토큰"으로 응답 시). 발송은 서버만.

### 2-5. 회원 탈퇴 (계정 삭제) `[결정됨 Q-009]`

**결정:** 앱 안에서 회원 탈퇴 가능. 탈퇴하면 **그 사람의 데이터를 전부 삭제**한다(지난 경기 출석·수상 포함). "탈퇴한 회원"으로 익명 보존하지 않는다.

**절차 (서버 함수 하나가 한 번에 처리, 서비스 키는 서버에만):**
1. 본인 확인(로그인된 본인만, 다른 사람 ID를 받지 않음).
2. **현재 팀장인 팀(해체 안 된 팀)이 하나라도 있으면 거절** — 위임 또는 해체 후에만 탈퇴 가능(유지).
3. 진행 중인 일정의 참석 응답 정리(아래 `[미결 M-22]`), 열려 있는 투표 처리(아래).
4. 카카오 "연결 끊기" 호출(구글은 토큰 철회). 애플 토큰 철회는 1차에 해당 없음.
5. 로고 등 저장소 파일 중 본인 소유가 있으면 삭제(1차에는 개인 사진이 없어 해당 없음).
6. 로그인 계정(`auth.users`) 삭제 → 아래 표의 삭제 동작이 연쇄로 적용된다.

**표마다 삭제 동작** — "같이 삭제"는 `ON DELETE CASCADE`, "비움"은 `ON DELETE SET NULL`. 모든 사람 칸은 `auth.users`가 아니라 `profiles.user_id`를 가리키고, `profiles`가 `auth.users`를 같이 삭제로 가리킨다.

### 3-1. 팀 `teams`

**무엇을 저장하나:** 팀 기본 정보(이름, 식별코드, 로고, 정기 운동일, 지정 풋살장, 인원 모집 여부).

| 이름 | 타입 | 필수 | 설명 |

  - 팀 검색: **모집 중이 아닌 팀도 포함** `[결정됨 Q-021]`. 이름·식별코드·로고·정기 운동일·구장 이름·팀원 수·모집 여부(화면의 "모집 마감" 표시용)만. 식별코드로 검색할 수 있게 할지는 Q-029와 함께 결정.
  - 초대 코드 확인: 유효한 코드일 때만, 그 팀의 이름·식별코드·로고만.
- 쓰기 (칸마다 다름):
  - 관리자가 직접 고칠 수 있는 칸: `name`, `logo_image_path`, `regular_*`, `venue_*`, `is_recruiting` (칸 단위 권한).
  - **`logo_text`: 팀장만.** 칸 단위 권한은 팀장과 운영진을 구분하지 못하므로, 직접 쓰기 칸에서 빼고 팀장 확인을 하는 서버 함수로만 바꾼다 `[결정됨 Q-014]`.
  - `team_code`: 생성 시 서버가 만든다. 앱에서 수정 불가(바꿀 수 있게 할지는 Q-029).
  - `id`, `created_by`, `created_at`, `dissolved_at`, `timezone`: 앱에서 수정 불가. 생성·해체는 서버 함수로만(해체는 팀장, 팀 이름 직접 입력 확인).
  - (security 반영) 그렇지 않으면 운영진이 `dissolved_at`을 직접 써서 팀장 전용인 해체를 우회할 수 있다.
  - (security 반영) 팀 검색·초대 확인 함수는 해체된 팀(`dissolved_at` 있음)을 항상 제외하고, 주소·좌표·장소 번호·만든 사람은 돌려주지 않는다.
- 로고 사진 저장소: 관리자만 올리기·지우기(사진 로고는 팀장·운영진 `[결정됨 Q-014]`). 추측할 수 없는 주소의 공개 저장소 `[결정됨 Q-027 S-10]`. 세부는 13장 S-10.

### 3-3. 팀 소속 `team_members`

**무엇을 저장하나:** 누가 어느 팀에 어떤 역할로 소속돼 있는지. 팀마다 한 줄씩이라, 한 사람이 여러 팀에 소속될 수 있다.

| 이름 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| id | ID | 필수 | |
| team_id | ID | 필수 | |
| user_id | ID | 필수 | 탈퇴 시 같이 삭제 |
| role | 선택(owner, manager, member) | 필수 | 팀장·운영진·팀원 |
| status | 선택(active, left, removed, dissolved) | 필수 | 소속 중 / 자진 팀 탈퇴 / 내보내짐 / 팀 해체 |
| joined_at | 날짜·시간 | 필수 | 합류 시각 |
| ended_at | 날짜·시간 | 선택 | 팀 탈퇴·내보내기·해체 시각 |

- 데이터베이스가 보장하는 규칙:
  - 팀당 현재 팀장은 정확히 1명.
  - 팀당 현재 운영진은 최대 2명.
  - 한 사람은 한 팀에 "소속 중" 줄이 최대 1개(재가입하면 새 줄).
- 팀 탈퇴·내보내기·해체 때 줄을 지우지 않고 status만 바꾼다(3-8). 회원 탈퇴 때는 줄을 지운다(2-5).
- 읽기: 그 팀 팀원(현재 소속 명단). 본인은 자기 소속 이력 전체.
- 쓰기: 서버 함수로만.
  - 운영진 지정·해제, 내보내기, 팀장 위임: 팀장만. 위임은 운영진 중에서만, 즉시 적용, 기존 팀장은 운영진으로.
  - **운영진도 바로 내보낼 수 있다**(먼저 해제할 필요 없음) `[결정됨 Q-018]`.
  - 운영진 지정·해제, 팀장 위임 받음, 내보내짐 → 본인에게 알림 `[결정됨 Q-022]` (9장).
  - 팀 탈퇴: 본인. 팀장은 위임 또는 해체 전에는 팀 탈퇴 불가.
  - 합류: 가입 승인 서버 함수가 생성.

- **팀 탈퇴·내보내기·해체 시 그 사람의 줄을 삭제** → 재가입하면 "미정"부터 `[결정됨 Q-015]`.

### 3-5. 초대 코드 `team_invites`

**무엇을 저장하나:** 관리자가 발급한 초대 코드. 24시간 뒤 자동으로 못 쓰게 된다.
**방식** `[결정됨 Q-002]`: 관리자가 공유한 링크를 열면 웹 페이지가 초대 코드를 보여주고 복사하게 한다. 앱을 설치한 뒤 첫 실행 때(또는 가입 화면에서) 그 코드를 붙여넣는다. 앱이 이미 설치돼 있으면 링크로 바로 열 수 있다. 유료 딥링크 서비스는 쓰지 않는다.

| 이름 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| id | ID | 필수 | |
| team_id | ID | 필수 | |
| token_hash | 글자 | 필수 | 코드 값의 암호화 지문(SHA-256). **원본은 저장하지 않음** `[결정됨 Q-020]` |
| created_by | ID | 선택 | 발급한 관리자. 탈퇴 시 비움(코드는 유효 유지) |
| created_at | 날짜·시간 | 필수 | 발급 시각. **서버 시계로만 기록, 앱이 지정 불가** |
| expires_at | 날짜·시간 | 필수 | 발급 시각 + 24시간. 트리거가 강제로 채우고 두 칸 수정을 막는다(S-13: 생성 칸으로는 불가) |
| revoked_at | 날짜·시간 | 선택 | 새 코드 발급·팀 해체로 무효화된 시각 |

- 코드 값: 서버가 만든 32바이트 무작위 값(사람이 추측 불가). 붙여넣기 방식이라 길어도 된다(손으로 칠 일 없음). 순번·팀 번호 등 추측 가능한 값은 넣지 않는다.
- **팀당 유효한 코드 1개** `[결정됨 Q-020]`: "무효화되지 않은 줄은 팀당 1개"를 데이터베이스 고유 조건으로 보장. 새로 발급하면 서버 함수가 이전 줄에 `revoked_at`을 찍고 새 줄을 만든다(한 번에). 만료만 되고 무효화 안 된 줄도 새 발급 때 같이 무효화한다.
- **24시간 안에 여러 명 사용 가능** `[결정됨 Q-020]`: 사용해도 줄이 닫히지 않는다.
- **다시 복사 불가**: 원본이 없으므로 다시 공유하려면 새로 발급한다(이전 코드 무효).
- **만료는 신청 시각 기준** `[결정됨 Q-020]`: 가입 신청(3-6)을 만든 시각이 만료 전이면 유효. 신청 후 승인이 만료 뒤에 이뤄져도 된다. 신청 후 코드가 재발급(무효화)된 경우 그 대기 신청을 그대로 둘지 `[미결 M-25]`.
- 사용 확인: 서버 함수가 "지문 일치 + 현재 시각 < 만료 시각 + 무효화 안 됨 + 팀 해체 안 됨"을 모두 확인. 실패하면 이유 구분 없이 "만료된 초대 코드예요" 처리(어느 코드가 존재했는지 알려주지 않기 위해). 사람당 가벼운 호출 제한(S-13).
- 링크 페이지: 코드 값은 URL의 `#` 뒤에 둔다(웹 서버 접속 기록에 안 남게, S-13).
- **팀 식별코드(3-1)와의 관계 `[미결 Q-029]`**: 식별코드가 "가입코드"로 쓰이면 초대 코드와 역할이 겹친다. 식별코드로 신청하는 경로를 "초대" 경로로 볼지 "검색" 경로로 볼지(=모집 꺼짐일 때 막을지), 둘을 하나로 합칠지 답을 받은 뒤 이 절과 3-6의 `via`를 고친다. **식별코드가 짧아 사람이 칠 수 있는 형태라면 추측 가능하므로, 그 자체로 모집 꺼진 팀에 신청할 수 있게 하면 안 된다**(security 재검토 대상).
- 읽기: 그 팀 관리자(발급 이력, 지문 칸은 제외). 팀원·외부인은 직접 읽기 불가.
- 쓰기: 서버 함수로만(발급: 관리자).

## 6. POM·오늘의 골 투표

### 핵심: "누가 누구를 찍었는지"를 저장하지 않는 구조

한 표가 들어오면 서버 함수 하나가 한 번에 두 가지만 기록한다.

1. **투표 참여 표시** — "OO가 POM 투표를 했다" (누구를 찍었는지는 없음)
2. **득표 집계** — "△△의 POM 득표 +1" (누가 찍었는지는 없음)

두 기록을 잇는 정보(투표 한 장 단위의 기록)는 어디에도 저장하지 않으므로, 앱 사용자(팀장 포함)는 어떤 경로로도 "누가 누구를 찍었는지" 알아낼 수 없다.
(security 반영) 단, 데이터베이스 최고 권한을 가진 운영자는 투표 진행 중과 백업 보관 기간 동안 데이터베이스 내부 기록(트랜잭션 번호, 변경 로그)으로 일부를 추정할 수 있는 여지가 남는다. 13장 S-02 참고.
그 대신 **한 번 낸 표는 바꾸거나 취소할 수 없다** `[결정됨 Q-027 M-08]`. 제출 전 확인 창을 띄운다.
투표 대상자가 3명 이하인 경기도 1위를 공개한다(소수라 추측될 수 있음은 감수) `[결정됨 Q-027 S-16]`.

### 6-1. 투표 회차 `award_polls`

**무엇을 저장하나:** 경기 하나의 POM·오늘의 골 투표 기간과 상태. 경기당 하나.

## 11. 데이터베이스 공통 규칙 (마이그레이션 작성 기준)

승인 후 builder가 따를 기준. 승인 전에는 마이그레이션을 만들지 않는다. Supabase 프로젝트는 서울 리전 `[결정됨 Q-024]`.

1. 모든 표에 권한 규칙(RLS)을 켠다. 규칙이 없는 표 = 아무도 못 읽는 표.
2. "그 팀 팀원인가 / 관리자인가 / 팀장인가"는 공용 확인 함수 3개로만 판단한다(`is_team_member`, `is_team_staff`, `is_team_owner`). 해체된 팀은 모두 거짓.
3. 규칙 검사가 필요한 변경(프로필 생성, 가입 승인, 역할 변경, 참석 투표, POM 투표, 배치 확정·확정 후 수정, 노쇼 표시, 로고 글자 변경, 부상 등록, 기기 주소 등록, 회원 탈퇴)은 서버 함수로만 하고, 앱이 표에 직접 쓰는 권한을 주지 않는다.
4. 서버 함수는 검색 경로를 고정하고, 호출자 확인(`auth.uid()`)을 함수 첫 줄에서 한다.
   - (security 반영) `SECURITY DEFINER` 함수는 모두 `SET search_path = ''`로 고정하고, 함수 안의 표·함수 이름은 `public.teams`, `auth.uid()`처럼 스키마까지 적는다.
   - (security 반영) `auth.uid()`가 비어 있으면(로그인 안 됨) 즉시 거절한다.
   - (security 반영) Postgres는 새 함수의 실행 권한을 기본으로 모두에게 준다. 함수마다 `REVOKE EXECUTE ... FROM PUBLIC, anon`을 하고 필요한 역할(`authenticated`)에만 다시 준다.
   - (security 반영) 공용 확인 함수(`is_team_member` 등)는 `team_id`만 받고 사람은 항상 `auth.uid()`로 판단한다. API에 노출되지 않는 별도 스키마(예: `private`)에 둔다. 소속 상태 `active` + 팀 `dissolved_at` 없음을 함께 확인한다.
   - (security 반영) 예약 작업 전용 함수(일정 자동 생성, 투표 마감·1위 선정, 출석 기록, 알림 발송)는 `authenticated`·`anon`에게 실행 권한을 주지 않는다.
   - (v2) 프로필이 없는 호출자는 프로필 생성 함수 외 모든 서버 함수에서 거절한다(Q-010).
5. 서비스 키는 서버 예약 작업과 서버 함수 실행 환경에만 둔다. 회원 탈퇴(계정 삭제)처럼 관리자 권한이 필요한 처리는 서버 함수 실행 환경에서만 한다.
6. 마이그레이션 파일 하나 = 변경 하나. 파일 이름은 `YYYYMMDDHHMM_설명.sql`. 승인본과 다른 표·칸을 만들지 않는다.
7. 실시간 변경 알림(Realtime)에는 공개해도 되는 표만 등록한다(득표 집계·투표 참여 표시·실력 등급·노쇼 표시 제외).
   - (security 반영) Realtime의 삭제(DELETE) 알림은 권한 규칙(RLS)이 걸러주지 않고 기본 키를 모든 구독자에게 보낸다. 등록하는 표는 기본 키가 무작위 `id` 하나뿐이어야 하고, 가능하면 줄을 지우지 않고 상태만 바꾼다. 게시(publication)는 표 이름을 하나씩 등록하고 "모든 표"로 만들지 않는다.
   - (v2) 회원 탈퇴는 여러 표의 줄을 실제로 지운다. Realtime에 등록한 표에서 탈퇴로 줄이 지워지면 무작위 `id`만 나가므로 위 조건을 지키면 문제없다.
8. (security 추가) 뷰(view)를 만들면 반드시 `security_invoker = true`를 붙인다. 실력 등급·득표 집계·투표 참여 표시·노쇼 표시를 읽는 뷰는 만들지 않는다.
9. (security 추가) 앱이 직접 쓰기를 허용하는 표는 (a) 수정 가능한 칸을 칸 단위 권한으로 제한하고, (b) `WITH CHECK`에서 바뀐 뒤의 `team_id`·`match_id`도 관리자 권한을 다시 확인하며, (c) `id`, `team_id`, `created_by`, `created_at`, `updated_by`는 앱이 바꾸거나 지정하지 못하게 한다(`updated_by`·`updated_at`은 트리거가 채움).
10. (security 추가) 권한 판단에 로그인 계정의 `user_metadata`(사용자가 직접 고칠 수 있음)를 쓰지 않는다. 카카오·구글이 넘겨준 이름·사진을 프로필에 자동 복사하지 않는다.
11. (security 추가) 기본 키는 무작위 uuid(`gen_random_uuid()`, v4)를 쓴다. 시간 순서 uuid(v7)는 배치 명단·투표 관련 표에 쓰지 않는다.
12. (security 추가) 함수 안에서 `RAISE NOTICE`/로그로 투표 후보·초대 코드 값·FCM 토큰·부상 메모를 남기지 않는다.
13. (v2) **사람 칸의 삭제 동작**: 사람을 가리키는 모든 칸은 2-5 표대로 `ON DELETE CASCADE`(같이 삭제) 또는 `ON DELETE SET NULL`(비움)을 반드시 적는다. 삭제 동작을 적지 않은 사람 칸은 만들지 않는다(적지 않으면 회원 탈퇴가 막힘). "비움"인 칸은 필수(NOT NULL)로 만들 수 없다.
14. (v2) **글자 수 검사** `[결정됨 Q-012]`: 정확한 "보이는 글자" 수는 앱(Flutter `characters`)이 센다. Postgres는 보이는 글자 단위로 셀 수 없으므로, 데이터베이스(또는 서버 함수)는 (a) 앞뒤 공백 없음, (b) 줄바꿈·제어 문자 없음, (c) 비어 있지 않음, (d) 코드 포인트 수 상한 = 글자 상한 × 8(이모지 조합 여유, 예: 팀 이름 80, 팀에서 쓸 이름 64, 자기소개·부상 메모 160)을 검사한다. 즉 앱을 조작하면 상한을 조금 넘길 수는 있어도 무한히 긴 값은 막힌다. 더 엄격히 하려면 서버 함수(Edge Function, `Intl.Segmenter`)에서 세는 방법이 있다(구현 단계 판단).

### 13-2. 상세

**S-01 (높음, 확인 필요) 같은 이메일 계정 자동 연결 — M-07**
- Supabase 공식 문서(Identity Linking)에 따르면 OAuth로 로그인할 때 **같은 이메일의 기존 사용자가 있으면 새 로그인 수단을 그 사용자에 자동으로 연결**하며, 이 기능은 "모든 사용자의 이메일이 고유하다"는 전제로 동작한다. 문서에는 **자동 연결을 끄는 설정이 나와 있지 않다**(2026-11-04 확인 시점). 끌 수 있는지 = **확인 필요**.
- 끌 수 없다면 security.md "이메일이 같다는 이유만으로 계정이 자동 병합되지 않는다"를 **지킬 수 없다**. 또 같은 이메일 계정 두 개가 공존할 수 없으므로 기획서의 "중복 가입 안내" 기능도 같은 이메일인 경우에는 발동할 상황 자체가 없어진다.
- 추가 확인 필요: Supabase 카카오 로그인이 카카오 이메일의 "인증됨" 여부를 어떻게 넘기는지. 인증되지 않은 이메일로도 자동 연결된다면 계정 탈취(미리 남의 이메일로 가입해 두기) 경로가 된다.
- 수동 연결(`linkIdentity`, 로그인된 본인만)은 프로젝트 설정에서 manual linking을 켜야 쓸 수 있다(문서상 베타). 계정 연결 기능의 전제 조건이다.
- 권고: Supabase 테스트 프로젝트에서 (1) 구글·카카오를 같은 이메일로 차례로 로그인했을 때 실제 병합 여부, (2) 자동 연결을 끄는 설정 유무, (3) 카카오 미인증 이메일 처리를 확인한다. 끌 수 없으면 lead가 kopn에게 "체크리스트를 '인증된 이메일만 자동 연결 허용'으로 바꿀지"를 물어야 한다. **확인과 결정 전에는 승인 불가.**

**S-02 (중간) 투표 익명성 잔여 경로**
앱 사용자 경로는 막혀 있다: 투표 참여 표시는 본인 것만, 득표 집계는 누구도 직접 못 읽음, 둘 다 Realtime 제외, 득표 집계에 시각 칸 없음. 남은 경로는 운영자(데이터베이스 최고 권한) 수준이다.
- 한 표를 한 트랜잭션에서 쓰므로, 투표 참여 표시 줄과 득표 집계 줄의 **트랜잭션 번호(`xmin`)가 같다.** 득표 집계 줄은 갱신될 때마다 바뀌어 마지막 투표자만 맞춰볼 수 있지만, 정리되기 전의 옛 줄(dead tuple), 변경 로그(WAL), 시점 복구용 백업에는 전체 순서가 남는다.
- Supabase 로그(API 요청 로그, Postgres 오류 로그)에 투표 함수의 인자(후보)가 남는지 = **확인 필요**. 요청은 반드시 POST 본문으로 보내고 URL 쿼리에 후보를 넣지 않는다.
- 권고: (1) 6장의 "개발자 누구도" 문구를 정확하게 수정함(반영). (2) 투표 마감 처리 때 해당 경기의 투표 참여 표시·득표 집계 줄을 한 트랜잭션에서 다시 써서 트랜잭션 번호를 같게 만들고, 이후 자동 정리(vacuum)로 옛 줄이 사라지게 한다. (3) pgaudit 같은 문장 감사 기록을 켜지 않는다. (4) 득표 집계 줄 미리 만들기, 투표 함수가 득표수를 돌려주지 않기, 기기·분석 도구에 투표 대상 남기지 않기(6-4 반영). (5) 2차 득표수 조회 함수는 **투표 마감 후에만** 숫자를 돌려준다(진행 중 여러 번 조회하면 단톡방의 "방금 투표했어" 같은 정보와 맞춰 추정 가능).
- 투표 서버 함수가 확인할 것: 호출자가 투표 대상자인지, 후보가 투표 대상자인지, 후보 ≠ 본인, 서버 시각 기준 투표 기간 내인지, 참여 표시 고유 조건으로 중복 차단(실패 시 전체 취소).

**S-03 (중간, 반영) 직접 쓰기 표의 우회**
- 초안의 `teams`는 "쓰기: 관리자"인데 칸 제한이 없어, 운영진이 `dissolved_at`을 직접 써서 팀장 전용인 해체를 하거나 해체를 되돌릴 수 있었다. `created_by` 위조도 가능 → 3-1 반영.
- `pairing_rules`는 "모순 검사는 서버 함수"인데 쓰기가 직접 허용이라 검사를 건너뛸 수 있었다 → 3-7에 서버 함수로만 명확화.
- `match_guests`, `skill_ratings`, `team_settings`, `lineups` 등 직접 쓰기 표는 `WITH CHECK`에서 바뀐 `team_id`를 다시 확인하지 않으면 자기 팀 줄을 다른 팀으로 옮길 수 있다 → 11장 9번 반영.

**S-04 (중간, 반영) SECURITY DEFINER 함수**
- 검색 경로 `''` 고정 + 스키마 명시, 로그인 안 된 호출 거절, `PUBLIC`·`anon` 실행 권한 회수, 공용 확인 함수는 `team_id`만 받기, API 비노출 스키마, 예약 작업 전용 함수 실행 권한 차단을 11장 4번에 반영.
- 공용 확인 함수가 `user_id`를 인자로 받으면 아무나 "이 사람이 이 팀 소속인가"를 물어볼 수 있는 조회 통로가 된다.

**S-05 (중간, 반영) 뷰** — Postgres 뷰는 기본이 만든 사람 권한이라 RLS가 적용되지 않고, Supabase는 `public` 스키마 뷰를 API로 노출한다. 11장 8번 반영.

**S-06 (중간, 반영) Realtime 삭제 알림** — Supabase 문서상 Realtime의 DELETE 이벤트는 RLS로 거를 수 없어 기본 키가 그 표의 구독자에게 간다. `attendance_responses`처럼 (경기, 사람) 묶음 키인 표를 등록하고 줄을 지우면 다른 팀 구독자에게 "이 경기에 이 사람"이 새어 나간다. 11장 7번 반영. Realtime 등록 표 목록은 구현 단계에서 security가 다시 본다.

**S-07 (중간) 부상 공개와 동의 철회**
- 팀원 읽기 규칙이 "등록할 때 동의가 있었다"만 보면 공개 동의를 철회해도 계속 보인다. **팀원 읽기 규칙 자체에** "주인의 두 동의가 모두 유효(철회 안 됨)"를 매번 확인하는 조건을 넣어야 한다(`user_consents`는 본인만 읽으므로 SECURITY DEFINER 확인 함수 필요).
- 동의 문구 버전이 바뀌면 재동의 전까지 비공개로 할지 = 정책 판단.
- 건강 정보는 개인정보보호법상 민감정보로 보인다(별도 동의 필요). 저장 시 추가 보호(암호화 등) 수준, 철회 시 삭제 범위(M-15)는 정책 판단.
- 알림 문구(복귀 확인)에는 부상 메모를 넣지 않는다(9장에 이미 있음). 잠금 화면 미리보기 문구도 문구 결정 시 고려.

**S-08 (중간) FCM 토큰 이전**
- 토큰은 전체에서 중복 금지인데 쓰기는 본인만이다. A가 로그아웃 없이(앱 삭제, 세션 만료) 기기를 넘기거나 같은 기기에서 B가 로그인하면 토큰 줄이 A 소유로 남아 **A의 알림(팀 이름, 일정, 가입 승인 등)이 B가 쓰는 기기로 간다.**
- 권고: 토큰 등록을 서버 함수로 하고, 같은 토큰이 다른 사람 소유면 현재 호출자에게 소유를 옮긴다. 로그인할 때마다 등록, 로그아웃 시 삭제, FCM이 "등록되지 않은 토큰"으로 응답하면 삭제.

**S-09 (중간) 확정 후 배치 수정** — 확정 후 수정은 "변경 이력 + 참석자 알림"이 규칙인데, 관리자가 `lineup_slots`를 직접 고칠 수 있으면 이력·알림을 건너뛴다. 권고: `status = confirmed`인 배치의 블록·명단은 직접 쓰기 금지, 서버 함수로만 수정(이력·버전·알림을 한 번에). 작성 중(draft)만 직접 쓰기 허용. `lineup_change_logs`의 before/after에는 사람 ID만 넣고 이름은 넣지 않는다(탈퇴 시 익명화 가능하도록).

**S-10 (중간) 로고 사진 저장소**
- 팀 검색·초대 확인 화면에서 팀원이 아닌 사람도 로고를 봐야 하므로 (A) 공개 읽기 저장소 + 추측 불가 파일 경로(`team_id/무작위값.jpg`) 또는 (B) 비공개 저장소 + 서버 함수가 짧은 유효기간의 서명 URL 발급 중 택일. 로고는 민감도가 낮아 A로 충분하다고 보지만, 공개 저장소는 삭제 후에도 CDN 캐시에 잠시 남는다.
- 어느 쪽이든: 파일 목록 조회(`storage.objects` SELECT)는 비팀원에게 열지 않음, 올리기·지우기는 경로 첫 폴더의 `team_id`로 `is_team_staff` 확인, 버킷에 용량 상한(예: 1MB)·형식 제한(jpeg/png/webp, **SVG 금지**).
- 휴대폰 사진에는 촬영 위치(GPS) 정보가 들어 있을 수 있다. 업로드 전 앱에서 다시 인코딩해 메타데이터를 지운다.
- 로고 교체 시 이전 파일 삭제, 팀 해체 시 처리(M-01)와 함께 삭제.

**S-11 (중간) 계정 삭제 — M-02**
- 애플 App Store와 구글 Play는 계정을 만들 수 있는 앱에 **앱 안 계정 삭제 기능을 요구**한다(구글은 웹 삭제 요청 경로도). 애플 로그인을 쓰면 삭제 시 애플 토큰 철회도 요구된다. 카카오도 "연결 끊기" 처리 필요. 따라서 M-02는 "할지 말지"가 아니라 "어떻게"의 문제다(세부 요구는 출시 전 다시 확인).
- 구조상 정할 것: `created_by`, `decided_by`, `updated_by`, `changed_by`, `ended_by`, `added_by`, `confirmed_by` 등 계정을 가리키는 칸이 많다. 외래 키 삭제 동작(`ON DELETE SET NULL` 등)을 정하지 않으면 계정 삭제가 막히거나 연쇄 삭제된다. A안(익명 보존)이라면 `award_winners`, `attendance_records`, `award_tallies`, `award_participants`, `lineup_slots`의 `user_id`를 널로 바꿀지 남길지 정해야 한다. ID만 남기고 프로필을 지우는 것은 가명 처리일 뿐, 같은 팀 사람에게는 누구인지 추정 가능하다.
- 삭제 권고 대상: 프로필, 선호 포지션, 부상·부상 이력, 기기 주소, 대기 중 알림, 가입 신청, 투표 참여 표시, 실력 등급, 그룹·라이벌 소속.
- 동의 기록(`user_consents`)을 증빙용으로 일정 기간 보관할지는 정책 판단.

**S-12 (낮음) 중복 가입 안내와 계정 열거**
- 함수가 **인자를 받지 않고** 호출자 본인의 로그인 정보에 있는 이메일만으로 확인하면, 남의 이메일을 넣어 가입 여부를 조회하는 통로가 되지 않는다. 이메일을 인자로 받는 형태는 금지.
- 공급자가 "인증됨"으로 표시한 이메일일 때만 안내한다. 인증 안 된 이메일로도 안내가 뜨면 남의 이메일로 가입 수단을 알아낼 수 있다.
- 반환은 "있음/없음 + 로그인 수단 종류"까지만(초안대로). S-01 결과에 따라 이 기능 자체가 필요 없어질 수 있다.
- M-05 A안의 "다른 계정에서 사용 중" 안내는 사용자가 그 로그인 수단의 주인임을 이미 인증한 뒤라 열거 문제 아님.

**S-13 (낮음) 초대 링크**
- 32바이트 무작위 값 + SHA-256 해시 저장이면 충분하다(느린 해시 불필요). 대입으로 맞힐 확률이 사실상 0이라 **대입 방지용** 횟수 제한은 필수가 아니다. 다만 가입 신청 남발·서버 부하 방지를 위해 초대 확인·가입 신청 함수에 사람당 가벼운 호출 제한을 권고.
- 구현 주의: `timestamptz + interval`은 Postgres에서 불변(immutable) 연산이 아니어서 생성 칸(generated column)으로 `expires_at`을 만들 수 없다. 트리거로 `created_at = now()`, `expires_at = created_at + 24시간`을 강제하고 두 칸 수정을 막거나, `expires_at`을 저장하지 않고 확인 시 `now() < created_at + interval '24 hours'`로 계산한다(어느 쪽이든 architect 판단).
- 링크가 웹 페이지(앱 미설치 시 스토어 이동)를 거치면 웹 서버 접속 기록에 링크 값이 남는다. 링크 값은 URL의 `#` 뒤(서버로 전송 안 됨)에 두거나 접속 기록에서 제외. Q-002(설치 후 이어서 가입)를 외부 딥링크 서비스로 하면 링크 값이 그 회사로 넘어간다(외부 서비스 추가 → kopn 결정).
- 링크가 새도 할 수 있는 일은 "가입 신청"까지이고 관리자 승인이 필요해 영향은 제한적이다.

**S-14 (낮음) 팀 검색** — 해체 팀 제외·주소/좌표 제외는 3-1에 반영. 추가 권고: 검색어 최소 2자, 결과 상한(예: 20개), `ILIKE` 특수문자(`%`, `_`) 이스케이프, 사람당 호출 제한(전체 팀 목록 긁어가기 방지). 팀 이름 중복 허용(M-04)이면 같은 이름 팀 사칭이 가능하나 가입이 승인제라 영향 낮음.

**S-15 (낮음) 실력 등급 간접 노출**
- 팀 나누기 계산을 관리자 앱에서 하든 서버 함수에서 하든, 저장 결과(배치·경고·변경 이력)와 공유 이미지에 등급·합계가 없으면 된다(초안대로). 공유 이미지 생성 코드는 등급 필드가 없는 화면용 데이터만 받게 한다.
- 관리자가 팀원으로 강등되면 서버 규칙으로 즉시 막히지만, 앱 기기 캐시에 남은 등급 목록도 역할 변경 시 지운다.
- 팀원 목록·내 기록 등 SECURITY DEFINER 함수가 `skill_ratings`를 조인하지 않는지를 코드 리뷰 항목으로 둔다.

**S-16 (낮음, 정책) 소규모 투표 추론** — 투표 대상자가 2명이면 "서로 찍었다"가 확정되고, 3명이면 1위 결과로 상당 부분 추정된다. 2차 "본인 득표수"가 붙으면 더 분명해진다. 구조로 막을 수 없어서, 최소 인원 미만이면 투표를 열지 않을지 등은 정책 판단.

**S-17 (낮음) `cast_on`** — 투표 참여 표시의 날짜 칸은 중복 방지·미투표 알림에 필요 없다. 최소 수집 원칙상 빼는 것을 권고(구조 변경이므로 architect 판단).

**S-18 (낮음) 기타**
- 관리자가 가입 신청자의 프로필·선호 포지션을 읽는 권한은 **대기 중 신청**에만 한정(거절·취소 후에는 불가).
- 게스트 이름은 동의 없이 입력되는 제3자 정보다. 이름(별명 가능)만 받는 현재 구조 유지. 보관 기간은 정책 판단.
- `notification_outbox`는 발송 후 일정 기간(예: 30일)이 지나면 삭제.
- 카카오 로그인 동의 항목은 최소로 요청하고, 공급자 정보를 프로필에 자동 복사하지 않는다(11장 10번).

### 13-4. 정책 판단이 필요한 항목 (lead → kopn)

v2 기준 해소 여부(architect 표시): 1 미결(Q-006-2) / 2 미결 / 3 미결(Q-028) / 4 **결정됨(Q-009, 전부 삭제)**, 동의 기록 보관은 Q-028 / 5 범위 **결정됨(Q-015)**, 보관 기간은 미결 / 6 **결정됨(Q-027 S-16)** / 7 **결정됨(Q-023)** / 8 Supabase **결정됨(Q-024 서울)**, 지도 서비스는 Q-032 / 9 **결정됨(Q-027 S-10, A)** / 10 **결정됨(Q-002, 외부 딥링크 안 씀)**

1. S-01: 자동 연결을 끌 수 없다면 체크리스트 "이메일 자동 병합 금지"를 바꿀지.
2. 개인정보 처리방침에서 투표 "익명"을 어떻게 표현할지(앱 사용자에게는 완전 익명, 운영자 수준 잔여 위험 존재).
3. 부상: 동의 문구(Q-003), 문구 버전 변경 시 재동의 전 비공개 여부, 철회 시 삭제 범위(M-15, `injury_events` 포함 여부), 공개 동의만 철회한 경우 처리.
4. 계정 삭제(M-02): 지난 기록 익명 보존 범위, 동의 기록 증빙 보관 기간.
5. 팀 해체·탈퇴 후 보관 범위와 기간(M-01), 게스트 이름·알림 대기열 보관 기간.
6. 소규모 투표(대상자 2~3명) 처리.
7. 14세 미만 가입 처리(법정대리인 동의 필요 여부 → 연령 확인을 할지).
8. 국외 이전 고지: FCM(구글), Supabase 서버 지역(서울 리전 여부), 지도 서비스.
9. 로고 저장소 공개(A) vs 서명 URL(B).
10. Q-002 설치 후 이어서 가입에 외부 딥링크 서비스를 쓸지(초대 링크 값이 외부로 전달됨).
